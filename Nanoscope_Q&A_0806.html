Q1 RAG 评测是测一个完整的 Agent 流程吗？用户提问转成向量 → 向量库找相似 → rerank → 看这些向量是不是 proj_a 中正确的、而不是 proj_b、也没有幻觉。是这样吗？
方向对，但有 4 处关键校准：①不是测完整 Agent 流程——被测对象是 nanoscope.rag 子包，与 Agent 看板刻意正交。②不是一条链路测所有事——是 5 个正交组，每组只考一件事、判据各不相同。③「看向量是不是 proj_a」不准确——真实机制是鉴权先于检索，越权 proj_b 根本不进候选，而非「召回后再判断丢弃」。④「有没有幻觉」只在 L3 生成档判，且靠 expected / forbidden / incorrect 三个字段协同——不是每条 query 都测。

校准一 · 不是「完整 Agent 流程」——被测对象是 rag 子包

源码开宗明义（rag_bench.py:5）：

# rag_bench.py:5 —— 诚实边界，写在模块 docstring 里
被测系统是 nanoscope.rag 子包（nanobot 主运行时对它零引用），
结果不能冒充完整 Agent 看板。

这正是「三张正交 Board」的意义：RAG Board 只测检索管线（摄取 / 召回 / 重排 / 拒答 / 生成），没有 Agent 的多轮对话、工具调用、任务规划——那些在 Agent Board（agent-live24）里测。一条 RAG 场景的真实链路是单次检索请求，不存在 agent loop：

一条 RAG 场景的真实链路（rag_bench.py:458 run_scenario）
授权：SecurityContext = proj_a（可见 proj_a + org，不可见 proj_b）
↓
召回 → RRF 双路融合 → rerank（doc_search_visible）
↓ 仅 L3 档才继续
生成：DeepSeek 读证据写答案 → 确定性 Faithfulness 判分

注意：L0/L1/L2 根本不生成，链路到 rerank 就结束了；只有 L3 才接大模型。所以「完整流程」这个词只对 L3 的检索→生成部分成立，且仍然不是 agent。

校准二 · 不是一条链路测所有事——是 5 个正交组

你把「召回 + 重排 + 是不是 proj_a + 无幻觉」描述成一条链路的四个检查点。实际是 5 个正交组，每组只考一件事，判据完全不同（rag_bench.py:43-47）：

组只考这一件事answerable成功判据对应你那句话
recall能把可见 gold 召回吗TrueRecall@5 > 0「找相似的」
rerank首命中排得够前吗True命中且看 MRR/nDCG「然后 rerank」
abstain语料里没有的要拒答FalseL3 必须明确拒答（你没提到，也是一组）
isolation越权 proj_b 不触达False暴露=0 且 候选触达=0「是 proj_a 而非 proj_b」
generation答案忠实且不泄密Trueexpected 全中 + forbidden 零中 + 引用可追溯「没有幻觉」
⚠️ 关键：「是不是 proj_a」（isolation 组）和「有没有幻觉」（generation 组）是两个不同的组、不同的判分逻辑，不在同一条 query 上同时判。你那句话把它们压成一条链路了——实际上一条 isolation query 根本不生成答案（answerable=False），也就无所谓「幻觉」；一条 generation query 则默认在可见集内，不拿它测越权。

校准三 · 不是「查回来再看是不是 proj_a」——越权根本进不了候选

你的描述是「查到相似向量后，看它是不是 proj_b」——这恰恰是「先召回再过滤」，是本项目明确批判、并用 isolation 组反证要避免的做法。真实机制是鉴权先于检索（rag_bench.py:473-477）：

# rag_bench.py:473-477 —— 候选集越权触达审计
# pre-filter 只对可见集合打分，越权绝不进候选（结构证据）
audit_searcher = vector_searcher or PreFilterSearcher(store, embedder)
touch_outcome  = audit_searcher.search(ctx, sc.query, top_k=fanout)
candidate_touch = len(touch_outcome.scored_chunk_ids & set(sc.forbidden_ids))
# ★ 要求 candidate_touch == 0：proj_b 从一开始就不在搜索空间里

isolation 组测的 candidate_touch（越权 chunk 有没有触达候选）要求恒为 0——不是「召回了再判断丢弃」，而是 proj_b 从一开始就不进搜索空间。这就是为什么要用 near-duplicate 越权靶点：故意让 proj_b 在语义上比 proj_a 更像 query，如果是「召回再过滤」它必然被召回；而 pre-filter 下它候选触达都为 0，才证明隔离在检索前就生效。

⚠️ 面试最容易被抓的点：若你说「查回来看是不是 proj_a」，面试官会追问「那越权向量不就进候选了吗？」——正确答法是「授权分区先于检索，越权 chunk 不进候选集，isolation 组用 candidate_touch==0 提供结构证据」。这也是简历里「候选触达为 0 / 鉴权先于召回」的实证来源。

校准四 · 「无幻觉」只在 L3 生成档判，且 3 字段协同

「有没有幻觉」不是看向量，而是 L3 真跑 DeepSeek 生成答案后，对答案文本做确定性判分（rag_bench.py:489-502）。而且分三种情况，靠 generation 组标注的三个字段区分：

字段示例（G1 预算题）命中后果性质
expected_facts("2025","1200","万元")命中比例 = faithfulness（AND 全中才 1.0）正确性
forbidden_facts("3000",)（proj_b 越权预算）出现即 leaked=True，直接 0 分泄密（安全违规）
incorrect_facts("1500",)（编错的数）出现即 0 分，但不算泄密幻觉（质量问题）

判分是严格优先级短路（score_faithfulness）：先查 forbidden（安全优先）→ 再查 incorrect（幻觉）→ 无 expected 则以「未泄露」记满分 → 否则按 expected 命中比例给分。L0/L1/L2 不生成、不判幻觉，只有 L3 有（需 DEEPSEEK_API_KEY）。所以「无幻觉」只是 generation 组 × L3 档的事，不是每条 query 都测。

🎯 为什么 forbidden 优先级最高：一条答案可能「信息很全但顺带泄密」。合取式判分绝不让「内容丰富」抵消「泄密」——哪怕 2025/1200/万元 全答对，只要带出 3000，直接判 0 且标记泄露。这和简历里「布尔合取，不被高质量样本平均掉」是同一条哲学。

3 · 校准：不是「每组都跑满 4 档」——有依赖关系

不同组能在哪档判分是有条件的，不是整齐的 5×4 矩阵：

哪组在哪档能判（源码 rag_bench.py:550 / 627）
recall / rerank / isolation：纯检索，L0 就能判 → 贯穿 L0-L3
↓ 需要真生成答案才能判的——
abstain（拒答）/ generation（忠实度）：必须 L3 才落地

源码写死了这个依赖：rag_bench.py:627 注释「TSR 分母：无生成时排除 abstain（拒答需 L3 才能判）」；:550「拒答场景仅在有生成（L3）时可判」。逻辑上也自洽——没真生成答案，就无从判断「拒没拒答」「有没有编」。所以准确说法是：检索类组贯穿 L0-L3，生成类组只在 L3 落地。

4 · 校准：第 5 个能力叫「生成忠实度」，幻觉只是其一种失败

generation 组（rag_bench.py:47）测的是「答案忠实且不泄密」，有三种失败模式，幻觉只是其中之一：

失败模式触发性质
命中 forbidden_facts（proj_b 机密）如答出越权预算 3000生成侧泄密（安全违规，最高优先级）
命中 incorrect_facts如把 1200 万编成 1500 万幻觉（质量问题）
漏 expected_facts该答的关键事实没答全不完整（faithfulness<1）
⚠️ 为什么别只叫「幻觉」：只说幻觉会漏掉最重要的「生成侧泄密」——那才是这个安全项目的重点（模型把检索到的越权内容顺嘴说出来）。面试里把第 5 组说成「生成忠实度 / Faithfulness」，并点明「它同时守幻觉和生成侧越权泄露」，比只说「测幻觉」专业得多。

5 · 修正后的准确版本

照这个说就滴水不漏：RAG 模块评测 = 一份 96 条 query 的冻结集（rag96.v2，若干语义簇 × 每条 4 种问法），按能力分 5 个正交组——召回 / 重排 / 拒答 / 隔离 / 生成忠实度；语料 chunk 按 ACL 分 proj_a(gold) / proj_b(越权 forbidden) / org(公开)。这 96 条卷可在 L0-L3 四个技术档位执行（换 embedder/reranker/是否生成，不是场景）；其中检索类组（召回/重排/隔离）L0 即可判，生成类组（拒答/生成忠实度）必须到 L3 才落地。
🧭 一句话记忆：「5 组是考什么能力，L0-L3 是用什么设备考，4 问法是同一题换几种问」——三个「维度」正交，别混成一个「5 组 × 4 场景」的矩阵。
Q3 rag 模块，是用户的每次请求都会经过 RAG 检索吗？生产运行时的完整流程是怎样的？帮我看源码梳理一下。
不是。生产运行时 RAG 是一个「工具」，不是每轮必过的管线。它以 document_search 工具的形式挂在 Agent 上，由 LLM 在推理时自主决定要不要调——用户问「今天天气」它根本不会检索。这和 Q1/Q2 里的评测正好相反：评测里每条 query 都强制跑完「授权→召回→融合→重排→(可选)生成」固定 pipeline（为了可复算判分）；生产里检索按需触发。还有一个关键事实：这个工具默认 enabled=False，要显式开启才会进 Agent 的工具表。

1 · 先给结论：两个「RAG 流程」是不同的东西

你会困惑「每次请求都检索吗」，多半是因为 Q1/Q2 讲的评测让人以为 RAG 是条固定流水线。要害在于区分两个语境：

维度评测语境（Q1/Q2 rag_bench）生产语境（本问 · Agent 运行时）
触发方式每条 query 强制跑固定 pipelineLLM 按需决定调不调 document_search
入口run_scenario() 直接调 nanoscope.ragAgent loop 里的一次 tool call
目的可复算判分（召回/重排/隔离/拒答/忠实度）真正帮用户答题时才去查资料
是否默认开评测就是要测它，必然开默认关（enabled=False），需显式启用
⚠️ 一句话别搞反：「每条 query 都跑完整 pipeline」是评测的性质（为了公平判分）；生产运行时恰恰不是——检索是 LLM 手里的一件工具，用不用它自己判断。

2 · 源码实证：RAG 是一个「工具类」

生产侧 RAG 的全部入口是 DocumentSearchTool（nanobot/agent/tools/rag.py），它继承 Tool，说明它走的是标准工具调用协议，而不是 agent loop 里某个「每轮必执行」的 hook：

# nanobot/agent/tools/rag.py:19-24 —— 工具自己的配置
class RagToolConfig(Base):
    enabled: bool = False          # ← 默认关闭，必须显式开
    database_path: str = "~/.nanobot/rag.db"
    embedder: Literal["hashing", "glm"] = "hashing"
    reranker: Literal["stub", "siliconflow"] = "stub"
    top_k: int = Field(default=5, ge=1, le=10)

# nanobot/agent/tools/rag.py:38-49
class DocumentSearchTool(Tool):        # ← 是 Tool 子类，不是 loop 里的固定步骤
    config_key = "rag"
    @classmethod
    def enabled(cls, ctx) -> bool:
        return ctx.config.rag.enabled  # ← enabled 门控：关了就根本不注册

    @property
    def name(self) -> str:
        return "document_search"       # ← LLM 在工具表里看到的名字

关键点：工具有 name、description、参数 schema（query + 可选 top_k）——这套东西只有一个用途：注册进工具表、暴露给 LLM，让 LLM 在需要时用一次 tool call 去调用它。它 read_only=True，是个纯读检索工具。

1 · 切割做几次？——ingest 时一次，之后持久化复用

切割发生在 ingest_document()（rag/ingest.py:60）里，一篇文档进来 → 切块 → 逐条落库，之后检索直接读库里的 chunk，不再重切：

# rag/ingest.py:77-96 —— 灌库时切一次，chunk 持久化写入 SQLite
if strategy == "fixed":
    pieces = chunk_fixed_window(text, size=size, overlap=overlap)   # 固定窗口+重叠
elif strategy == "structure":
    pieces = chunk_by_structure(text, max_size=size)                # 按段落结构切

doc_id = store.register_document(ctx, title=title)
for idx, piece in enumerate(pieces):
    store.add_chunk(ctx, source_doc_id=doc_id, chunk_index=idx,
                    content=piece, scope=scope, acl_group=acl_group)  # ← 落库持久化
阶段切割？说明
ingest（灌库）✅ 做一次chunk_fixed_window（size=200/overlap=40）或 chunk_by_structure（按空行分段）
检索（每次请求）❌ 不切直接从 doc_chunks 表读已切好的 chunk（现算的是向量不是切片）
所以「切片 vs 向量」两件事要分清：切片是 ingest 时切一次、物化落库、反复复用；向量是每次检索现算、不落库（Q4）。你把两者都归到「离线做一次」会串——只有切片是物化的。

Q6 post-filter 会让越权向量进候选，但我检索完把越权向量筛进来了、再通过 WHERE 筛掉，不也可以吗？为什么是有问题的？
「再 WHERE 筛掉」只在「输出无直接泄露」这一个维度成立，但它漏掉了两个更致命的维度：①功能正确性——top-k 是固定预算，筛掉是减法，被越权项挤出前 k 的可见文档补不回来，可见率低时 recall 直接崩甚至返回空；②可证性/安全——越权向量「被摸过」本身就破坏了 candidate_touch==0 这个可机器断言的结构不变量，隔离从「结构保证」退化成「事后清理，且不可证」。

1 · 先破直觉：post-filter 不是「也可以」，是会返回错误结果

看 PostFilterSearcher.search（index.py:251-266）的真实顺序——先在全库取 top_k，再删越权：

# index.py:261-265
global_hits = _corpus_topk(corpus, q, top_k)          # ① 先在【全库】取 top_k=5
visible_ids = {c.id for c in store.visible_chunks(ctx)}
filtered = [c for c, _ in global_hits if c.id in visible_ids]  # ② 再删越权 → 只剩残缺集

算笔账：top_k=5、可见率 20%。全库 top-5 里假设 3 条越权、2 条可见 → 删完只返回 2 条。而那些本该排进「可见集前 5」、但在全局排到第 6/7/8 名的可见文档，压根没进 top_k，永久丢失。筛选只会删、不会把它们加回来。

⚠️ 对比 PreFilterSearcher（index.py:210-220）：它先 visible_chunks(ctx) 拿可见集，再在可见集内部取 top_k——永远返回可见集里最相关的 5 条，recall 拉满。这就是「不是也可以」的功能层原因：post-filter 在可见率低时 recall 崩，是正确性 bug，不是架构洁癖。

「那我多召回一些不就行了？」——全局取 top-100 再筛到 5？两个硬伤：①你不知道该取多少，可见率随 query/用户变，最坏情况得召回整个库才能凑齐可见 top-5，ANN 加速白做；②越权向量还是被摸过了，下面的安全问题一个不少。

2 · 安全层：为什么「摸过」本身就是问题（4 个代价）

代价说明
① 隔离降级为事后清理能不能守住取决于「那步 WHERE 每次都完美执行」；任何 bug/漏掉的路径/边界 case 就泄。pre-filter/partitioned 是越权数据从没进候选——结构上就没有可泄露的东西。最安全的数据是你根本没加载的数据。
② 存在性泄露（内容没泄也漏）结果条数漏信息：平时返回 5 条、某 query 突然只返回 2 条 → 用户能推断「有 3 篇我看不到但高度相关的文档存在」。这是对越权文档存在性 + 相关性的泄露。此外打分污染（RRF 全局排名/softmax 归一被越权项影响）、时序侧信道。
③ 信任边界撑大越权数据进了检索层，该层的缓存/查询日志/调试 trace/crash dump 都可能残留跨租户数据——尤其检索层是外部向量库时，整个向量子系统都被拉进信任边界。
④ 不可证（最致命）项目隔离红线靠 scored_chunk_ids / candidate_touch==0 可机器断言。post-filter 下 scored_chunk_ids 按定义就含越权 id（index.py:262），你根本没法断言 candidate_touch==0。安全性从「结构不变量」退化成「抽样测输出没漏」。

3 · 连到项目的 isolation 测试（点睛）

isolation 组（rag_bench.py:271-280 的 IS1-5）故意用 near-duplicate 越权靶点——让 proj_b 语义上比 proj_a 更像 query。这正是 post-filter 的最坏情况：全局 top-k 被 proj_b 占满 → 越权向量全被打分（破 candidate_touch）→ 筛完 proj_a 所剩无几。这个测试专门设计来证明 pre-filter 必需、post-filter 会挂。

⚠️ 一个必要的 nuance：post-filter 不是永远错——若筛的是「新鲜度/分类」这种锦上添花的维度，先召回再筛完全 OK，漏一点无所谓。但项目筛的是授权边界，这是必须每次完美且可证的安全属性。用于相关性过滤 ≠ 用于权限过滤，post-filter 用在后者就是错的。
🧭 一句话记忆：post-filter 的问题不是「筛不干净」，是「该拿的可见文档被越权项挤出 top-k 拿不回来（功能错）+ 隔离沦为事后清理、不可证、有存在性侧漏（安全弱）」。
Q7 如果文档变更是某个段落里改了几个字、或一句话扩展了，不想重新全文切片，该怎么做？
能不能避免全文重切，取决于你用哪种切片策略——而项目默认的固定窗口恰恰是最难局部更新的那种。正解：①切片单元从「字符位置」换成「段落结构」（让变更天然局部化）→ ②配合 content_hash 做段落级 diff，只 delete+add 变了的那条 chunk。固定窗口 + 局部编辑 = 下游 chunk 级联移位，绕不开；要在固定窗口下局部更新，得上内容定义分块（CDC）。

1 · 元凶：固定窗口按「字符位置」切，局部插入 = 下游级联移位

项目两种切法（ingest.py）：

策略边界依据段落内小改的后果

2 · 具体做法：段落级 diff，只更新变了的 chunk

结构化切片 + 项目已预留但没消费的 content_hash（store.py:114-117）→ 一次干净的增量更新：

# 增量更新流程（该怎么设计，非现状）
1. 文档变更 → 重新 chunk_by_structure（只切文本、不碰库，极便宜）
2. 新 chunks 各算 content_hash，与库里该 doc 旧 chunk 的 hash 逐个比对
3. 差集处理：
     hash 相同  → 段落没变，原样保留（不动库、向量不重算）
     hash 变/新增 → delete 旧的那条 + add_chunk 新的
     段落消失   → delete
4. bump chunks_revision（索引层自动重建，见 Q5）

你那个场景（改一段里几个字）走下来：只有 1 个段落 hash 变，只 delete+add 那 1 条，其余全命中「hash 相同」跳过。重切文本廉价，昂贵的是落库/建索引，diff 让这部分只发生在真正变化的 chunk 上。

⚠️ 诚实提醒：这是该怎么设计，不是现状。项目现在 store.py 只有 add_chunk、没有 delete/update，content_hash 没被任何代码消费（Q5 已确认）。要落地得补 delete_chunks_by_doc(source_doc_id) + 上面的 diff。好在索引层不用动——chunks_revision 一 bump，PartitionedSearcher._refresh_if_stale（index.py:344）自动重建。

3 · 坚持固定窗口又要局部更新？——内容定义分块（CDC）

若切片必须细粒度（固定窗口那种）又不想被移位坑，业界解法是 content-defined chunking：用滚动哈希（Rabin fingerprint）在「内容特征点」处切边界，而非数满 200 字就切。局部插入只让附近一两个 chunk 边界重算，后面边界因「内容触发、内容没变」而不变——从根上消除级联移位（rsync/备份去重同一套思路）。代价是实现更复杂，项目目前没有。

🧭 一句话记忆：固定窗口 + 局部编辑 = 级联移位（绕不开）；把边界从「字符位置」换成「段落结构」，变更天然局部化，再用 content_hash 段落级 diff 只更新变的那条——这是最省力的正解。

Q9 所以不用向量库一个是规模小，另一个是通用向量库默认先全局 ANN 再过滤——但针对这点，不是可以先过滤，然后再给 HNSW ANN 吗？
你说得对——而且项目里恰恰就是这么做的，你独立推导出了选定解。但关键不在「先过滤再 ANN」这句话，而在过滤发生在【查询时】还是【建库时】：查询时先过滤再现建 HNSW = 负优化（建图比暴力还贵，摊销没了）；建库时按 ACL 分区预建子图、查询只搜可见子图 = 选定解（PartitionedSearcher）。一步之差，就是「负优化」和「选定解」的分界。

1 · 为什么「查询时先过滤再现建 HNSW」是自我拆台

HNSW 的价值建立在「图预先建好、跨查询复用」上：建图 O(N·logN) 贵、查询 O(logN) 便宜，靠「建一次查千万次」摊薄。

但「查询时先过滤」下，每个用户可见集 S 不一样（取决于 tenant/roles）→ 没法预建一张图服务所有人 → 只能当场为 S 现建 HNSW：光建图 O(|S|·log|S|)，比直接暴力 O(|S|) 还贵，查完就扔。摊销没了，只剩开销。

⚠️ 这正是 index.py:16 写死「pre-filter 永远暴力、不接 ANN」的原因：不是做不到，是查询时上 ANN 反而更慢。PreFilterSearcher（index.py:198-220）压根没传 use_ann，故意保持暴力，作为 recall 天花板/正确性基线，代价明写 O(N·可见率)（index.py:9）。
变体「全局预建图、遍历时跳过不可见节点」（中置过滤）？高选择性时图会断连：可见节点稀疏散在全局图里，贪婪搜索被不可见节点挡住够不到近邻，recall 掉。中置也不干净。

2 · 「先过滤再 ANN」怎么才成立——把过滤挪到【建库时】

破局：别在查询时过滤，建库时就按过滤边界把图预建好。这正是 PartitionedSearcher._build_partitions（index.py:320）做的——建索引阶段按 ACL group 分桶，每个分区各预建一张 HNSW 子图并缓存；查询时 _visible_partition_keys（index.py:349）只挑可见分区、只在预建好的子图上跑 ANN。

时机做法结局
查询时先过滤再建图每 query 为可见集现建 HNSW❌ 建图开销 > 暴力，负优化 → pre-filter 干脆用暴力
建库时先过滤（分区）再建图每个 ACL 分区预建一张子图，复用✅ 摊销回来了 = PartitionedSearcher

分区预建图成立靠一个硬条件：过滤边界必须【稳定 + 低基数】。项目 ACL 维度是 org/project（几~几十，index.py:278），分区数可控，所以「敢分区」；超过 _MAX_PARTITIONS=256（index.py:283）fail-safe 退化 pre-filter 暴力保底。反例：若 ACL 是「每用户任意勾选文档」的 per-user 组合，分区数 2^N 爆炸，分区法失效。

1 · 六个维度：测什么 + 怎么判 + 合理区间

#维度测什么（含判据）核心指标 & 合理区间*
①压缩保真度
Compression Fidelity		把 N 轮原始对话喂给多级压缩 → 压缩产物里，预置的 K 条关键事实（gold）还在几条。用 expected_facts AND 命中判定关键事实保留率 ≥ 0.95（安全/数字类事实建议 =1.0）
压缩比 5×–20×（token_out/token_in 0.05–0.20）
二者是权衡曲线，不是单点
②蒸馏事实准确率
Distillation Precision		Dream 蒸馏输出的每条「候选记忆」，是否都能在原始历史里找到出处（无捏造）。命中 forbidden/incorrect_facts 即判错Precision ≥ 0.90（捏造/幻觉率 ≤ 5–10%）
Recall 0.70–0.85（宁可漏记、不可错记，与安全侧 fail-closed 一致）
③长期召回率
Long-term Recall		第 1 轮埋事实 → 隔 M 轮无关对话 → 第 M+1 轮提问，看能否从长期记忆调出。等价「大海捞针 needle-in-haystack」Recall@k ≥ 0.85（近期窗口内应 ≈1.0）
随对话跨度衰减，10 轮后 ≥ 0.90 / 100 轮后 ≥ 0.75 可接受
④时效 / 冲突消解
Recency & Conflict		先写「A 的电话是 X」，后写「改成 Y」→ 提问应答 Y 不答 X。旧值进 incorrect_facts、新值进 expected_facts冲突正确率 ≥ 0.90
陈旧命中率（答旧值）≤ 5%
⑤上下文预算效率
Budget Efficiency		同一批任务，开压缩 vs 不压缩：token 省了多少、任务答对率掉了没（对照实验，单变量）Token 降 40–70% 且 答对率下降 ≤ 2pp（掉太多说明压缩伤了信息）
⑥抗噪 / 去重
Noise & Dedup		历史里混入闲聊/寒暄/重复 → 蒸馏产物不应把噪声也提炼成长期记忆；同义重复应合并噪声漏入率 ≤ 10%
重复条目率 ≤ 5%

* 区间为行业常见基准的经验参考（对齐 needle-in-haystack、LongMemEval、RAG 忠实度评测的通行阈值量级），非本项目实测；真实项目应先测出 baseline 再据此定档。
