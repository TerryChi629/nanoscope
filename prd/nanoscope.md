## 0. 一句话

> nanobot 是一个为"**单人 · 本地**"设计的 Agent 框架。本项目的统一命题是:**让一个 nanobot 实例经 IM 接入、安全地服务一个团队/社区的多个用户**——这个场景背景同时逼出了记忆系统与并发调度的真实缺陷,而这些缺陷是否被真正修好,由一套旁路的评测底座量化验证。
>
> **为什么是 IM bot 而不是"多人共用一个部署"**:"多个用户连一个 bot"是 IM bot 的**入口定义**(一个群里不可能给每人配一个 bot),多用户不是运维选择、是形态内生;而跨用户泄露发生在框架**内部数据流**(Dream 蒸馏→全局 Core),鉴权网关拦不到。所以"必须改框架内核"在这里是必然,不是我硬凹。(对比论证见 §1.2)
>
> **目标规模先钉死(贯穿全文)**:本项目瞄准的是 **N ≈ 20~30 并发会话**(一个活跃团队/中小社区"同时在飞"的 turn 数)。在这个区间内,单进程单事件循环 + 应用层调度足够。**单进程的适用上界 M 不预设成一个固定数字(不写死"50 后 CPU 必成瓶颈")**——真实拐点由 B1 压测下的**事件循环 lag、队列等待、RSS、Provider 限流、P99 曲线**共同确定(第一瓶颈很可能不是 CPU,而是 Provider 的 RPM/TPM 或文件/SQLite 写竞争)。下文所有"无需水平扩展"的论断,都特指"目标规模 N 内、未触及实测拐点 M"这个区间——不是无条件成立。"**实测出 M 在哪**"本身就是项目结果之一,不是先写答案再验证。

## 0.1 B1 / B2 / B3 是什么(先立定义,后文不再重复解释)

| 代号 | 全称 | 一句话定义 | 角色 |
|---|---|---|---|
| **B1** | 执行链路追踪与评测底座 | 一套**不侵入 Agent 主循环**的可观测底座:通过 Hook 旁路采集**质量类**指标(token、工具调用、三粒度延迟、Recall@K/MRR/nDCG、forbidden-hit),并在调度层 `loop.py` 单独埋点采集**工程类**指标(gate 饱和度、队列深度、锁等待、P50/P99、Jain fairness),两路数据汇入**同一套 trace 存储 + 报表**。 | **证据平面(非主角,验证 B2/B3 是否有效)** |
| **B2** | 可评测的记忆系统重构 | 把基线"单人全局共享 + 全量注入"的记忆,改造成 **scope 硬隔离(安全,命题:跨用户零泄露 `forbidden_hit=0`)+ RAG 混合检索(相关性)** 的两层架构(详见 §4.1)。 | **承重腿 · P0(核心价值)** |
| **B3** | 单进程 asyncio 应用层并发调度优化 | 在**不做部署层水平扩展**的前提下,对基线的全局信号量 + per-session 锁做应用层调度增强(有界公平准入为主,gate 分级 / 令牌桶 / 背压 / 优先级队列为可选深度,详见 §4.3)。 | **第二数据点** |

> 三者不是三个并列功能,它们的关系是一条因果链,见 §0.2。

## 0.2 项目主线:场景承重,记忆隔离是承重腿,B1 是证据平面(已决策)

> ⚠️ 这是本项目**最容易被答辩官攻击的点**:"你这最硬的一件事到底是什么?" 如果答"追踪 + 记忆 + 并发都做了",立刻掉回"功能堆叠";如果答"我做了个通用评测平台",会被归类为"日志 + 报表(plumbing)"。**这里一次性拍死,后文 §5 状态列、§6 边界均以此为准。**

**决策(v2.1 重定位):主角是"真实场景逼出的改进",承重腿是 B2 记忆隔离(P0 安全命题);B3 并发是同一上游逼出的第二数据点;B1 评测底座是把前两者的收益变成数据的证据平面——不是主角。**

**为什么不再把 B1 当唯一柱子(吸收第二轮 review):** "能度量"是手段,"消除跨用户泄露"是目的。把手段供成柱子,答辩官一句"JSONL + Hook + HTML 不就是结构化日志和报表"就能看穿;而且"平台很通用"是个**证伪不了的形容词**(测两个样本 ≠ 通用)。把主角换成"我修好了单用户框架进多用户时的安全漏洞",承重命题变成 `forbidden_hit == 0` 这个**可判定的布尔值**,一票否决、可复现——更可防守。**B1 上一版的所有投入一行不浪费,只是从"主角"重挂到"证明主角成立的证据"。**

因果链(一个上游场景 → 两类改进 → 一套证据):

```
        真实场景:一个 nanobot 实例经 IM 接入,多用户共用(群 + 私聊)
        (单用户框架被拿去做多用户 → 缺陷内生,不是我硬凹)
                        │
        ┌───────────────┴───────────────┐
   多用户→隐私问题                    多用户→争抢问题
        │                                 │
   B2 记忆隔离(承重腿·P0)          B3 并发调度(第二数据点)
   命题:跨用户零泄露(forbidden_hit=0)  命题:撑得住 N 并发、公平不饿死
   scope 硬隔离 + 混合检索             有界公平准入(+可选深度)
        └───────────────┬───────────────┘
                        │  两类改进都需要"改前 vs 改后"的数据来证明
        ┌───────────────▼───────────────┐
        │   B1 证据平面(不侵入主循环)      │
        │  质量面:Hook 采 Recall@K/forbidden-hit/延迟/token │
        │  工程面:loop.py 埋点采 P99/队列深度/Jain fairness │
        │  同一套 trace + 报表 → 飞书演示看得见            │
        └────────────────────────────────┘
```

**为什么这样拍板:**

1. **它把主角从"手段"换成"目的",承重命题从形容词换成布尔值。** 答辩问"最硬一件事",答案是唯一的:**我识别出 Agent 从单用户走向多用户时 identity/session/memory-scope 被错误耦合(框架自身的 bug),重构了 principal-aware 隔离并 fail-closed,消除跨用户长期记忆泄露**;B1/B3 都是围绕这条主线的证据与延伸。这比"我做了个评测平台"更接近真实后端 / AI-Infra 项目。
2. **两类改进不是并列拼盘,是同一上游逼出的两个面。** 共同上游只有一个——"单用户框架被用于多用户 IM bot"。多用户 → 隐私 → B2;多用户 → 争抢 → B3。所以是一条因果链,不是功能堆叠。
3. **两条腿的硬度不同,必须分主次(这是承重的意义)。** B2 命题 `forbidden_hit=0` 是 2 用户即触发的安全硬伤,布尔可判定——**承重腿**;B3 命题"撑得住 N"随规模恶化、需实测曲线——**第二数据点**。即使 B3 被质疑"20~30 人真需要调度优化吗",项目也塌不了,因为承重腿在 B2。
4. **B1 是证据不是主角,所以 B1 够用即可,不追求平台级完整;B2 必须无懈可击。** B1 只需能落 `forbidden_hit / Recall@K / P99 / Jain fairness` 这几条、支撑"改前 vs 改后"A/B;B2 的隔离必须 fail-closed、Dream 后门堵死、`forbidden_hit=0`(见 §4.1)。

> **这条钉死后:** ① §4.3 并发定位为"第二数据点",MVP 收敛到**有界公平准入**能被 B1 测出差异即止,不膨胀成独立调度器;② §4.1 的核心卖点压在"scope 硬隔离 + 混合检索的记忆重构"上;③ §5 状态列、§6 边界、§7 简历句均以"B2 承重 / B3 数据点 / B1 证据"为准。

## 1. 背景转变:使用场景迁移了

### 1.1 原设计:单人 · 本地 · 多设备

nanobot 的每一个默认值都写着"个人助手"。这不是猜测,是代码里的自证:

| 证据 | 位置 | 泄露的假设 |
|---|---|---|
| 全局并发闸门**默认值 3**(非硬编码,`Semaphore(_max)`,`_max` 读环境变量默认 3;`≤0` 则退化为无限) | `agent/loop.py:311-315` | 默认给到"我自己 + 偶尔几个后台任务"的量级——**官方给的默认就是个人级** |
| 并发数只是**环境变量**、不是 config 字段 | `NANOBOT_MAX_CONCURRENT_REQUESTS`(`loop.py:312`) | 官方没把它当需要认真运维、随场景调优的旋钮(config schema 里根本没有它) |
| `unified_session` 注释写 **"single-user multi-device"** | `config/schema.py:148` | session 隔离的设计目标是"单人多设备",不是多人 |
| workspace **全局唯一一份** | `config/schema.py:122`;`agent/loop.py:373`;`agent/context.py:63` | MEMORY/SOUL/USER 只有一份,默认所有人共享 |
| inbound/outbound **无界队列** | `bus/queue.py:17-18` | 个人用户不会瞬间灌几百条,不需要背压 |
| **无**多租户 / per-user 隔离 / ACL | (全仓搜 tenant/multi_user/per_user/acl 无记忆隔离命中) | 只有一个"我",不存在用户间抢占与隐私边界 |

### 1.2 新场景:团队/社区共用一个 IM Bot

**"多用户"在这里不是运维选择,是 IM bot 的入口形态内生的——这一点直接堵死软肋。**

一个 nanobot 实例接上飞书/Slack/Discord,进了一个团队工作群或社区群,**群里所有成员天然都在和同一个 bot 说话**(群聊)+ 各自私聊它(1:1)。这就是 IM bot 的定义,和"课题组 IT 主动选择共用部署"有本质区别:

| 反问 | 课题组共用部署(旧场景,撑不住) | 团队/社区 IM bot(新场景,反问失效) |
|---|---|---|
| "为什么不每人部署一份?" | 答不利索——确实可以每人本地各跑一份 | **一个群里给每人配一个 bot = N 个 bot 挤在群里,荒谬**。多用户是入口形态强制的 |
| "为什么不外面包多租户网关?" | 答不利索——正常就该包网关 | **网关拦不到泄露**:泄露发生在框架内部数据流(私聊内容被 Dream 蒸馏进全局 Core 再注入给别人),鉴权/路由网关够不到这一层(见 §3.1 路径③) |
| "这需求真吗?" | 偏产品(省钱省运维),弱 | nanobot **本就自带 IM 接入 + 群聊 session**(`channels/*`),这个形态是官方支持的,不是我硬造 |

**新场景下"共用"的真实收益(顺带,不作为承重理由)**:
- **一个 bot 服务一群人**是 IM 产品的常态(客服 bot、社区问答 bot、团队助手 bot),无需辩护。
- **共享组织知识**:团队规范、文档、FAQ 可作为共享记忆(`scope=org`),全员受益——但这是加分项(P2),不是承重腿(见 §4.2)。

### 1.3 关键区分:共用什么 / 隔离什么

IM bot 场景里"共用"和"隔离"必须分层,混为一谈会掉坑:

| 维度 | 应该共用? | 说明 |
|---|---|---|
| **入口 / 实例**(一个 bot 服务一群人) | ✅ 共用 | IM bot 的定义,天经地义 |
| **群聊里的对话消息**(谁在群里说了什么) | ✅ 群成员可见 | 这是 IM 平台的物理事实,与 nanobot 无关 |
| **组织知识**(规范/文档/FAQ) | ✅ 共用 | `scope=org`,全员受益 |
| **个人长期记忆 / 画像 / 私聊事实** | ❌ **必须隔离** | bot 沉淀出的"关于某人的结论"不该注入给别人;私聊内容更不该被蒸馏进全群可见的 Core |

> **⚠️ 这里要澄清一个直觉陷阱**:"群里所有人都能看到消息,那还谈什么隐私?"——**"对话消息互相可见"(IM 物理事实)和"bot 把你的话沉淀成长期画像后共享给所有人"(nanobot 的记忆层行为)是两回事**。前者天经地义,后者是泄露。而且私聊(1:1)内容根本不在群里,却会被 Dream 汇入全局 Core 泄露给全群——详见 §3.1。
>
> **健康形态 = 共用入口 + 共用组织知识 + 按 `sender_id` 隔离个人长期记忆**。这正是当前 nanobot **没做完**的——它在对话 session 层按 sender 隔离了,却在长期记忆层(Core/Dream)漏了(见 §3.1 的"隔离只做了一半")。

## 2. 这个背景如何逐一击穿基线假设

一旦从"单人"切到"多用户",1.1 的每条假设都会失效,且有明确顺序:

| 失效顺序 | 触发规模 | 失效的假设 | 现象 |
|---|---|---|---|
| ① 隐私边界崩塌 | **只要 2 个用户** | Core 记忆全局共享 | A 的长期记忆被无条件注入给 B(见 §3.1) |
| ② 并发闸门崩 | **4 个用户同时问**(默认 gate) | gate 默认 3 | 第 4 个排队;而 Agent turn 常几十秒~数分钟,"同时在线"概率极高 |
| ③ 容量爆炸 | 记忆随时间累积到拐点 | Core 全量注入 | 长期运行的 bot,几十用户的画像/事实全挤进一份 MEMORY.md 每轮全量注入,拐点由 B1 实测(见 §3.1) |
| ④ 慢会话饿死快会话 | 有人跑长任务时 | 无公平调度 | 一个数据分析 agent 占着 gate 名额,全群等 |
| ⑤ 洪峰堆积 | 群里同时刷屏 | 无界队列 + 无限 create_task | task 堆积、内存与延迟一起爆 |

> **注意**:① 隐私是"2 个用户即触发"的**安全硬伤**,不是规模问题;②③④⑤ 是随规模恶化的**性能/容量问题**。两类问题性质不同,解法也不同。

## 3. 背景暴露的两类真问题

### 3.1 记忆系统:隐私泄露(承重腿 · P0)+ 容量爆炸(拐点由 B1 界定)

**根因一句话**:Core 记忆(MEMORY.md)是**全局唯一一份 + 每轮全量注入**(`agent/context.py:86-88`;`agent/memory.py:233-235`),SOUL/USER 同理(`agent/context.py:80-82, 166-177`)。多用户共用一个 bot 时同时触发两害。

#### ★ 关键发现:框架的隔离"只做了一半"(这是本项目最硬的动机)

这是回应"群里所有人本来就互相可见,还谈什么隐私"的核心论据,请务必讲清楚:

**nanobot 自己已经认可"群成员的记忆该分开",并在对话 session 层做了 per-sender 隔离——但长期记忆层(Core/Dream)没跟上。前门锁了,后门大开。**

| 层 | 群聊里隔离了吗 | 机制 / 证据 |
|---|---|---|
| **入站消息带发送者身份** | —— | `InboundMessage.sender_id`(`bus/events.py:25`)——**框架认得"谁说的"** |
| **对话 session(当轮消息)** | ✅ **已按 sender 隔离** | 群里开 `group_user_isolation` 时 session_key = `{name}:group:{conversation_id}:{sender_id}`(`channels/dingtalk.py:698-699`);飞书 `topic_isolation` 默认 True 按话题切 session(`channels/feishu.py:357, 2255-2259`) |
| **Core(MEMORY/SOUL/USER)** | ❌ **未隔离** | 全局一份、无条件注入所有 session(`agent/context.py:86-88`) |
| **Dream 蒸馏** | ❌ **未隔离** | 读历史调 `read_unprocessed_history(since_cursor)`,签名**无 `session_key`**,所有用户历史混进一个 prompt→蒸馏进全局 MEMORY.md(`agent/memory.py:367-369, 490`) |

> **一句话叙事(答辩王牌)**:框架费劲按 `sender_id` 把群里每个人的当轮对话隔离开了——**说明官方自己都认为"群成员的记忆边界该分开"**;可它转头让 Dream 把每个人(含私聊)的私人事实无差别蒸馏进一份全局 MEMORY.md,再注入给全群每个人。**我做的不是无中生有加隔离,而是把框架自己开了头、却没贯通到记忆层的隔离补全。** 这比"我从外部提一个需求"强一个量级——是框架自身逻辑不自洽的 bug。

**(A) 隐私泄露——三条路径,一条比一条隐蔽**

| 路径 | 机制 | 触发条件 | 证据 |
|---|---|---|---|
| ① Core 文件必然泄露 | MEMORY/SOUL/USER 无条件全量注入到每个用户的每轮 | **默认单 workspace 下必然** | `context.py:86-88, 166-177` |
| ② 群聊 / unified 历史泄露 | 群未开隔离 / `unified_session=True` 时读到他人 session 历史 | 群聊未开 `topic_isolation`/`group_user_isolation`,或 `unified_session=True` | `memory.py:394-399`;`keys.py:5,8-11`;`channels/feishu.py:357`;`channels/dingtalk.py:698` |
| ③ Dream 无过滤汇入 Core(最隐蔽,连私聊都泄露) | Dream 读历史调 `read_unprocessed_history(since_cursor)`——**签名无 `session_key` 参数**,只按 cursor 切,**所有用户(含 1:1 私聊)的历史都进同一个 Dream prompt**,蒸馏后写进全局 MEMORY.md,再经路径①泄露给全群 | 即使群聊 session 隔离全开、`unified_session=False` 也发生 | `memory.py:367-369`(签名无 session_key)、`memory.py:490`(Dream 调用点)、`memory.py:482-504`(prompt 拼装) |

> **路径③ 为什么最致命**:群聊 session 隔离(路径②的防线)**只管当轮对话可见性,管不到 Dream**。用户私聊(1:1)跟 bot 说的话,群里根本没有,却会被 Dream 蒸馏进全群可见的 Core。**这是"连私密渠道都守不住"的泄露,也是网关绝对拦不到的(它在框架内部数据流上)。**
>
> **路径③ 措辞纪律**(答辩用,避免被现场翻代码打脸):不要说成"读全量再由 LLM 筛"——弱版本,会被"那 LLM 可以筛掉啊"化解。**准确说法:`read_unprocessed_history` 在数据可见性层面就不带 `session_key` 过滤(`memory.py:367-369` 签名可证),所有用户历史在进 LLM 之前就已混入同一个 prompt——泄露发生在"喂进去"这一步,不依赖 LLM 是否愿意筛。**

**🎬 可现场复现的泄露演示脚本**(飞书群 + 私聊):
1. 用户 A **私聊** bot:"我下周要离职,先别跟组里说。"
2. 等 Dream 低频触发一次(或手动触发)——A 的这句话被蒸馏进全局 `MEMORY.md`。
3. 用户 B 在**群里**问 bot:"最近组里有什么人事变动吗?"
4. bot 从全局 Core 抖出 A 的离职计划回答 B。**一个跨用户、跨渠道(私聊→群)的泄露事故,现场可复现、可录屏。**

**(B) 容量爆炸(拐点不硬拍,交给 B1 实测)**
```
长期运行的 bot:几十个用户的偏好/事实 → 全挤进一份 MEMORY.md → 每人每轮对话全量注入
                 → token 随时间线性上涨 + 信噪比下降(prompt 里塞着其他所有人的无关记忆)
```

> ⚠️ **不硬断言"到 X 条就必须 RAG"**(那是可证伪的空话)。**容量拐点由 B1 规模曲线实验测出**:在不同记忆规模下画 grep vs BM25 vs RRF 的 Recall@K,找 grep 开始失效的交叉点。RAG 检索这条腿的价值不在"我断言几十人就爆",而在"**我用数据判断它从什么规模、什么查询类型开始划算**"。承重腿始终是隐私隔离 P0(2 用户即触发),容量/RAG 是随规模恶化、由数据界定的第二性问题。

**记忆隔离现状汇总**(唯一维度是 session_key,且只覆盖到对话层):

| 记忆层 | 隔离? | 机制 | 强度 |
|---|---|---|---|
| Core(MEMORY/SOUL/USER) | ❌ 完全不隔离 | 全局文件,无条件注入 | 零 |
| session.messages(当前对话) | ✅ 物理隔离(群里按 sender 切) | 按 session_key 分文件(`session/manager.py:428-430`);群 `group_user_isolation`/`topic_isolation` | 强 |
| history.jsonl(历史注入) | ⚠️ 条件隔离 | 读取时 session_key 过滤,全局一个文件(`memory.py:391-392`) | 脆弱 |
| Dream 蒸馏路径 | ❌ 不隔离 | 读历史无 session_key 过滤(`memory.py:367-369`) | 零(后门) |

> **结论:多用户共用一个 IM bot,个人长期记忆一定跨用户泄露,只是快慢问题。** 默认配置下群/私聊的**当前对话**隔离了(框架做了一半),但**长期记忆 Core 完全共享,且 Dream 会把私聊内容偷偷汇入全群可见的 Core**(框架没做完的另一半)。

### 3.2 并发调度:个人级模型撑不住多人

**当前并发模型**(已核实):单消费者主循环(`agent/loop.py:873-882`)→ 全局 Semaphore(**默认 3,由环境变量 `NANOBOT_MAX_CONCURRENT_REQUESTS` 决定,`≤0` 无限**,`loop.py:311-315`)→ per-session Lock(`loop.py:301, 974`)→ per-session pending Queue(maxsize=20,`loop.py:305, 977`)。**两层并发,零限流 / 零优先级 / 零背压 / 零公平 / 无压测脚本。**

**澄清一个常见误解**:它不是"单线程一次处理一个 turn"。asyncio 单线程事件循环可以"同时在飞"多个 turn(默认最多 3);turn 是 IO 密集(等 LLM/工具),`await` 时事件循环切给别的 turn。真正的并发上限是**人为设的默认 gate=3**,不是线程。

> **措辞纪律**(答辩用):不要说"3 是写死的",会被一句"环境变量能改"驳回。**精确表述是:官方默认 3、藏在环境变量里而非 config、且没有分级/公平/背压——`3` 本身能调,但"没有调度策略"这件事调不掉,这才是 B3 的靶子。**

多用户下的崩溃链见 §2 的 ②④⑤。

## 4. 由背景推导的改进

### 4.1 记忆:scope 硬隔离 + RAG 检索(两层正交)★ 核心

这是本项目最硬的动机。**必须把"隔离"和"检索"分成两个正交层——用检索做权限是安全灾难。**

| 层 | 问题 | 手段 | 性质 | 决定 |
|---|---|---|---|---|
| **第一层:隔离** | 这条记忆**该不该给这个用户看?** | **scope 硬过滤**(SQL `WHERE`) | 确定性、安全边界 | 能不能看 |
| **第二层:检索** | 能看的里,**注入哪几条最相关?** | **RAG**(BM25/向量/RRF) | 概率性、相关性排序 | 注入哪些 |

**红线**:RAG 是语义相似度,概率性、会漂移。**用它决定可见范围 = 算错一次 = 泄露一次**。安全边界只能是确定性的墙。这也是 GPT5.6 强调的"**scope 过滤必须发生在召回前,不是召回后再隐藏**",且**过滤必须收在 Repository 内部,上层不许自己拼 WHERE**(避免任何一处漏拼就穿墙)。

**正确管道(隔离在前,检索在后)**:
```
用户 A 提问 → 解析出 PrincipalContext(tenant_id, principal_id)
   ↓
① scope 硬过滤(墙,在 Repository.search_visible 内部强制,调用方传不进 owner):
   WHERE tenant_id=? AND ( scope='org' OR (scope='user' AND owner_id=?) )
   ↓  ← 确定性地挡掉 B 的私人记忆,零泄露;DB 层再加 CHECK 兜底
② 在 A 可见范围内 RAG 检索:BM25/向量/RRF 排序取 Top-K
   ↓  ← 解决容量+信噪比,只注入相关的,替代全量注入
③ 注入 prompt
```

**scope 分层**:

| scope | 内容 | 可见性 | 注入方式 |
|---|---|---|---|
| `user` | 个人记忆/偏好/对话事实 | `owner_id` 本人(= principal_id) | 硬过滤 + 检索注入 |
| `org` | 团队/社区规范、文档、FAQ | 同 `tenant` 内全员共享 | 硬过滤 + RAG 检索 |

> DB 层用 CHECK 约束把"`scope='user'` 必须有 `owner_id`、`scope='org'` 必须无 `owner_id`"钉死,缺字段写入直接失败(fail-closed),不给"默认可见"留缝。

**owner 锚点 = 从 `sender_id` 派生的 `principal_id`(一等字段,不从 `session_key` 反推)**:

> ⚠️ **P0 修正(吸收第二轮 review)**:上一版说"owner 直接取 `sender_id`、把 `session_key → sender_id` 解析补上"——**这条在群聊里不成立**。默认 `session_key = channel:chat_id`(`bus/events.py:32-35`)**不含发送者**;群聊只有开 `group_user_isolation` 才把 sender 塞进 session_key(`channels/dingtalk.py:698-699`),`unified_session=True` 时更是所有人塌成 `unified:default`(`session/keys.py:5-11`)。**一个 `session_key` 可能对应多个 owner,绝不能拿它反推 owner。**

必须把**四种 ID 拆成互不推导的独立字段**:

| 概念 | 含义 | MVP 取值 |
|---|---|---|
| `tenant_id` | 组织/社区边界 | 配置里的固定常量(一个 bot = 一个 tenant),留字段不建管理系统 |
| `principal_id` | **认证用户 = 真正的 owner** | `channel + ":" + sender_id`(`sender_id` 见 `bus/events.py:24`) |
| `session_key` | 对话连续性 / 串行化边界 | 沿用框架现有 `channel:chat_id`(`events.py:32-35`) |
| `trace_id/run_id` | 一次执行的观测边界 | B1 生成 |

正确链路是 `InboundMessage → IdentityResolver → PrincipalContext(tenant_id, principal_id) → SessionContext(session_key) → MemoryScope`,**`principal_id` 与 `session_key` 解耦、各存各的,不互相推导**。

- **这仍然坐实 §3.1 的"补全"叙事**:框架每条入站消息本就带 `sender_id`(还用它切过 session),我只是把它**升格为一等的 `principal_id` 并一路穿到长期记忆层**——不是无中生有,是把框架半途丢弃的身份补全贯通。
- **`principal_id` 必须在写 history 时就持久化**(基线 `append_history` 只可选存 `session_key`、不存发送者,`memory.py:239-290`),否则 Dream 事后无从追溯 owner——这是闭合后门(职责③)的前置。
- 跨渠道/跨设备把多个 `sender_id` 合并成同一自然人,是"自建 identity 映射层"的活,**明确列为范围外**(见 §6),不在 MVP。

**两个动机独立,IM bot 场景两者都占**:
- **隔离(scope)由"多用户"逼出**——哪怕记忆很少,只要多用户共用一个 bot 就必须做,否则泄露(2 用户即触发,P0)。
- **检索(RAG)由"记忆量随时间累积变大"逼出**——由 B1 规模曲线界定从什么规模开始划算(§3.1(B))。

**隔离层的三条职责(缺一条,墙就有后门)**:

1. **召回前过滤**:所有检索(含 §4.2 的 org 知识)都必须走 `Repository.search_visible(principal, query, top_k)`,由它**内部**强制 `WHERE tenant_id=? AND (scope='org' OR (scope='user' AND owner_id=?))`(`owner_id` = 当前 `principal_id`),再做相关性排序——上层拿不到拼 WHERE 的机会,不是召回后再隐藏。
2. **写入时打标**:任何写进结构化语料的记忆,都必须带 `tenant_id + scope + owner_id(=principal_id)`;缺字段的写入被 DB CHECK 直接拒绝(fail-closed),不允许"默认可见"。owner 由运行时从 `PrincipalContext` 注入,**不进工具 schema、模型无法伪造**。
3. **闭合 Dream 后门(修复 §3.1 路径③)——分 MVP / P1 两步,MVP 用确定性做法,不让 LLM 判 owner**:
   - **问题**:基线 Dream 走 `read_unprocessed_history`(无 session_key/owner 过滤)→ 把多人历史拼成一个 prompt(`memory.py:482-504` 只留时间+内容)→ 蒸馏 → 写全局 MEMORY.md,是绕过隔离墙的后门。
   - **MVP 做法(fail-closed,确定性)**:`multi_user.enabled=true` 时**直接禁止 Dream 写个人记忆 / 禁止 Dream 改全局 `MEMORY.md`/`USER.md`**;个人记忆只经显式 `memory_remember` 工具写入(该工具带 §职责2 的打标)。单用户模式保持原行为不变。
     - **为什么 MVP 不做"按 owner 蒸馏"**:那需要 LLM 从混着多人的 prompt 里判断每条事实归谁——**这又是概率性边界,违反本节红线**。所以 MVP 直接关掉这条路,是最省事又零泄露的选择。
   - **P1 做法(owner-aware,仍确定性)**:history 写入时持久化 `principal_id` → 按 `principal_id` **分批**构造各自独立的 Dream prompt(在进 LLM 前就切开)→ Dream 只输出 `MemoryCandidate` 候选、**确定性继承该批次的 principal_id**(不由 LLM 指定 owner)→ 后台事务合并入库。
   - **这是 B2 隔离层与 Dream 的接口契约,必须在开发指导里落成明确任务**,否则 §4.1 建的墙会被 Dream 从后门绕过。

> **一句话**:`tenant_id + scope + owner_id(=principal_id)` 不只是"检索时的过滤维度",它是**贯穿写入(打标)→ 后台蒸馏(Dream 分派 owner)→ 召回(WHERE 前置)整条链路的隔离锚**。只在检索端加 WHERE、却放任 Dream 无标签写 Core,等于装了防盗门却把后窗大开。

### 4.2 共享知识:scope=org 的 RAG

团队/社区共享知识**比个人记忆更适合 RAG**——它把 RAG 生效的前提全占了:

| RAG 生效前提 | 个人记忆 | 团队/社区共享知识 |
|---|---|---|
| 量大到塞不进 context | ✗ | ✓ 规范+文档+FAQ 轻松上万条 |
| 语义查询多 | 中 | ✓ "报销流程"要命中"费用申请指引" |
| 多人复用同一份 | ✗ | ✓ 一份索引全员用,成本摊薄 |
| 相对静态可预建索引 | ✗ 一直变 | ✓ 文档更新频率低,适合离线建索引 |

> **这把"规模曲线"论据从人造数据集升级成真实业务场景**:团队/社区知识库天然处在"grep 开始失效、RAG 开始划算"的规模区间。
>
> ⚠️ **边界**:这是"文档问答 RAG",难点在 **chunking(切分)** 不在检索算法(BM25/RRF 是标准件)。若做,chunking 才是技术深度所在;且它是独立工程,**不能白嫖进现有排期**——列 P2 或简化实现。

> 🧱 **承重结构声明(回应"别让共享知识 RAG 变成叙事承重墙")**:让"多人共用**刚需**改造"这条腿**刚性成立的,是 §3.1 的隐私隔离(P0,2 人即触发的安全硬伤)**,不是共享知识 RAG。共享知识 RAG 只是"**顺带能做、体现我懂 RAG 全貌**"的加分项(P2)——它被降级 + 难点是脏活(chunking),完全不影响项目立得住,因为承重腿不在它身上。
>
> **自洽性检查(必须保持一致)**:凡是对外的一句话卖点(简历句、§7 结尾叙事、方案文档定位),**核心卖点必须压在"scope 硬隔离 + 混合检索的记忆重构"上,共享知识 RAG 只能作为"另外还做了 org 知识库 RAG"的附加句**。若哪里把"共享知识 RAG"写成核心卖点,就与这里的 P2 定性自相矛盾,需改回。(已核对:§7 结尾叙事与《方案文档》定位均以记忆重构为核心,未把共享知识 RAG 抬为卖点——一致。)

### 4.3 并发:应用层调度优化(不做部署层水平扩展)

**两个层次解耦,本项目只做应用层:**

| | 应用层调度优化 ✅ 做 | 部署层水平扩展 ❌ 不做 |
|---|---|---|
| 解决 | 单进程内几个 turn 怎么调度更公平抗压 | 一个进程不够 → 多进程一起扛 |
| 手段 | gate 分级、优先级队列、令牌桶、背压、慢会话隔离 | 多实例 + 负载均衡 + 分布式锁 + 外置 MQ |
| 天花板 | 单进程能力(IO 密集下可达几十并发) | 理论无限 |
| 适合本项目? | ✅ 后端味浓、可用压测证伪 | ❌ 性价比低、超出"魔改一个项目"范畴 |

**为什么应用层够用——先给数字,再给结论(不给数字的"无需扩展"是可证伪的空话)**:

- **目标规模 N ≈ 20~30 并发会话**(一个活跃团队/中小社区"同时在飞"的 turn 数,不是注册人数)。turn 是 IO 密集(绝大部分时间在 `await` LLM/工具),单进程单事件循环在这个量级扛得住——**瓶颈是人为默认 gate=3,不是事件循环本身**。把 gate 调大 + 加公平性/背压,一台机器覆盖 N 无压力。
- **单进程适用上界 M 不预设固定值**:不写死"50 后 CPU 必成瓶颈"。真实拐点由 B1 压测下的**事件循环 lag、队列等待、RSS、Provider RPM/TPM 限流、SQLite/文件写竞争、P99 曲线**共同确定——第一瓶颈很可能先来自 Provider 限流或写竞争,而非 CPU。**"M 在哪"是项目要测出来的结果,不是先写的答案。**
- **所以"无需水平扩展"这个论断,严格限定在"N 内、未触及实测拐点 M"的区间**。它不是"nanobot 永远不用扩展"的断言,而是"**在目标规模内应用层调度是正确的性价比选择;我能用压测数据指出天花板 M 在哪、以及越过 M 之后该换部署层方案**"的工程判断。

> **答辩防守(对"那 100 人呢"这类问题)**:直接承认——"100 并发会话大概率已过单进程实测拐点 M,那时应当上多实例 + 负载均衡,这是部署层的事;我这个项目的边界画在目标规模 N=20~30,并**用压测数据给出实测 M**,证明区间内应用层调度足够。" 把 N 钉死、M 交给实测,论点就从"容易被推翻的断言"变成"知道边界怎么测出来的判断"。
>
> ⚠️ **N 是目标设计规模(工程估计),M 是待实测拐点**:N 先钉一个可辩护的数字锁定范围,M 由 B1 压测回填(§4.4)——"目标先定、上界实测"本身就是"数据驱动界定边界"的体现,而不是先写答案再验证。

**优化菜单(MVP 只做第 0 项,其余为可选深度)**:
0. **有界公平准入(MVP · 唯一必做)**:全局有界 admission 队列 + per-principal 最大在途数 + principal round-robin + 队列满快速失败/retry-after。一步同时压住 §2②(并发上限)、§2④(慢会话饿死)、§2⑤(洪峰堆积),且能被 B1 用 `queue_wait_p99 / Jain fairness / rejected_total` 直接测出前后差异。
1. 调大 / 分级 gate → 更细地解 §2② 并发上限。
2. per-user 令牌桶限流 → 更平滑地解"一人刷屏占满资源"。
3. 独立优先级队列 → 更进一步解 §2④(在 round-robin 之上分优先级)。

> 采集指标以 GPT5.6 建议为准:`queue_wait_p50/p95/p99`、`completion_latency_p95/p99`、`throughput`、`rejected_total`、`event_loop_lag`、**Jain fairness index**、每 principal completed turns。**公平性用 Jain 指数量化,不写"是否饿死"这种口头判断。**

> ✅ **定位已决策(见 §0.2)**:B3 = **第二数据点**,不是与 B2 并列的第二根承重腿,也不是独立调度器项目。MVP 只做上面第 0 项(有界公平准入),做到能被 B1 测出 `queue_wait_p99` 收敛、`Jain fairness` 提升即止;第 1~3 项列为"有数据支撑再做"的可选深度。

### 4.4 可观测:B1 作为证据平面

B1(Trace/评测)在这个背景下的角色是**证据平面**(见 §0.2)——它自己不是主角,而是把 B2/B3 的改造收益变成**可复现、可判定**的数据,支撑"改前 vs 改后"A/B。三类指标各有承重分量:
- 量化 **B2 隔离(承重命题)**:`forbidden_hit`——跨用户/跨渠道能否抖出他人私人记忆,**承重命题是 `forbidden_hit=0`**(布尔可判定、一票否决、可复现,见 §3.1 复现脚本)。这是整套证据里分量最重的一条。
- 量化 **B2 召回**:Recall@5 / MRR / nDCG / 端到端成功率,画 grep/BM25/RRF 规模曲线找交叉点(界定"从什么规模该上 RAG",§3.1(B))。
- 量化 **B3 并发**:`queue_wait_p50/p95/p99` / `completion_latency_p95/p99` / throughput / `rejected_total` / `event_loop_lag` / **Jain fairness index** / 每 principal completed turns,画"用户数→延迟劣化"曲线找**实测拐点 M**(§4.3),公平性用 Jain 指数量化而非口头判断"是否饿死"。

> **注意采集点差异**:B1 的 `TraceHook` 挂在 **AgentRunner** 生命周期(经 `Nanobot.run(hooks=)` 注入,`nanobot.py:136/156`);但并发指标(锁等待/队列深度/gate 饱和)发生在 **AgentLoop._dispatch** 层(`loop.py:964-978`,在 runner 之前,Hook 够不到)。**B3 可复用 B1 的 JSONL 落盘 + HTML 报告,但采集点要在 loop.py 另埋。** 不是白嫖。

## 5. 背景 → 问题 → 改进 → 模块 总映射

| 背景暴露的问题 | 性质 | 改进 | 对应模块 | 状态 |
|---|---|---|---|---|
| 隐私泄露(Core 全局共享 + Dream 无过滤) | 安全硬伤(2人即触发) | principal-aware scope 硬隔离(召回前 WHERE)+ 闭合 Dream 后门 | **B2** | **承重腿 · P0(核心价值)** |
| 记忆容量爆炸 + 信噪比崩塌 | 容量(规模恶化) | RAG 检索注入替代全量注入 | **B2** | 已确立(附于承重腿) |
| 团队/社区共享知识散落 | 能力缺口 | scope=org 的文档 RAG | **B2** 扩展 | P2 / 简化实现(加分项,非承重) |
| 并发闸门默认 gate=3、无公平、无背压 | 性能(规模恶化) | 有界公平准入(+可选深度)+ 压测 | **B3** | **第二数据点:收敛到能测出差异即止(见 §0.2)** |
| 缺可观测 / 无法量化收益 | 证据缺失 | 旁路 Trace + 评测 + 报告 | **B1** | 已确立(**证据平面,非主角**) |

> **主线只有一条 = 场景逼出的改进,承重腿 = B2 记忆隔离(P0)**;B3 是同一上游逼出的第二数据点,B1 是把两者收益变成数据的证据平面(见 §0.2)。这不是三线并行,是"一个场景 → 两类改进 → 一套证据"。

## 6. 诚实边界(明确不做什么)

| 不做 | 原因 |
|---|---|
| **部署层水平扩展**(多实例/负载均衡/分布式锁) | 单进程 asyncio 在目标规模 N=20~30 内足够(§4.3);越过实测拐点 M 才需扩展,超出魔改范畴 |
| **企业级多租户平台**(完整权限矩阵/审计/增量索引/跨渠道 identity 合并) | 是产品不是简历项目;`tenant_id` 只留常量字段、不建管理系统,跨渠道合并同一自然人明确范围外(§4.1) |
| **用 RAG 做权限/可见范围** | 概率性手段做安全边界 = 泄露灾难;隔离必须是确定性硬过滤 + Repository 强制 + DB CHECK(§4.1) |
| **MVP 阶段 owner-aware 的 Dream 蒸馏** | MVP 直接禁 Dream 写个人记忆(fail-closed);owner-aware 分批蒸馏列 P1,不让 LLM 判 owner(§4.1 职责③) |
| **完整文档管理系统**(共享知识 RAG 的重工程部分) | chunking/导入/权限是独立工程,列 P2,不白嫖排期;它是加分项不是承重腿(§4.2) |
| **把 B3 做成生产级完整调度器** | B3 是第二数据点,只需正确 + 能被 B1 测出差异;MVP 只做有界公平准入(§0.2、§4.3) |
| **把 B1 平台化 / 三线并行当三根柱子** | 违背 §0.2 的"场景承重 · B2 为 P0 承重腿 · B1 为证据平面";B1 够用即可,不追平台级完整 |

## 7. 为什么这个背景让动机"可防守"

这是本文档的终极价值——它给了每个改进一个**扛得住面试追问**的动机:

1. **隐私泄露是 P0 bug,不是优化**(承重腿)。面试官不会问"这优化有必要吗",因为跨用户泄露长期记忆是安全事故——且命题可判定(`forbidden_hit=0`,一票否决、可复现)。这比"给记忆加检索"(可选优化)强一个量级——**"多人共用刚需改造"这条腿,是靠隐私隔离撑起来的,不是靠共享知识 RAG**(§4.2)。而且这是**框架自身逻辑不自洽的 bug**:它已按 sender 隔离对话 session,却让 Dream 把私聊事实无差别汇入全局 Core(§3.1)——我做的是补全,不是无中生有。
2. **规模拐点是物理真实且靠数据界定的**。默认 gate=3 摆在代码里、几十用户画像塞爆 context 是算得出的——不像人造数据集需要辩护"你是不是造题"。目标规模 N=20~30 先钉死,**上界 M 不预设而由 B1 压测实测**(§4.3),**"无需水平扩展"是"目标内成立、且我能测出天花板在哪"的工程判断,不是可被"那 100 人呢"一句推翻的空话**。
3. **一条主线贯穿,而不是三个功能并排堆**(见 §0.2)。答辩问"最硬一件事"只有一个答案:**我修好了单用户框架被用于多用户 IM bot 时 identity/session/memory-scope 被错误耦合导致的跨用户泄露**;B3 是同一上游逼出的第二数据点,B1 是证明这些改造有效的证据平面。有一以贯之的因果链(场景 → 两类改进 → B1 证据 → 飞书演示),而不是孤立技术点堆砌。

> **最终一句话叙事(供简历/答辩定调,数据出来后再补 X%)**:
> 基于开源 Agent 框架 nanobot,针对其"单用户假设"被用于**多用户 IM bot**(飞书/Slack,群 + 私聊)时暴露的缺陷做魔改。**核心(承重)**:识别出 identity/session/memory-scope 被错误耦合导致跨用户长期记忆泄露(含 Dream 把私聊事实蒸馏进全局 Core),重构 **principal-aware scope 硬隔离 + 混合检索**的记忆层——scope 过滤收在 Repository 内部、DB CHECK 兜底、fail-closed,实现跨用户零泄露(`forbidden_hit=0`)并以 RAG 替代全量注入解容量。**延伸**:对单进程 asyncio 调度做**有界公平准入**优化,缓解慢会话饿死与洪峰堆积。**证据**:自建不侵入主循环的旁路 **Trace + Benchmark 底座**,以 Recall@K / MRR / forbidden-hit / P99 queue-wait / Jain fairness 对改造前后做可复现 A/B,并用规模曲线界定"什么规模该做、单进程天花板在哪"。
