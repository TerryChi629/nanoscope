Q1 Recall@k 中 gold =「人工标注的标准答案 chunk 集」是什么？
一句话：gold（金标准）是「对某个 query，事先由人 / 规则认定『这几条 chunk 才是正确答案』的那个 id 集合」。它是评测的裁判标尺——检索器返回一串结果后，拿它去对答案：命中 gold 的算对，没命中的算错。没有 gold，Recall/MRR/nDCG 全都无从算起。

1 · 为什么必须先有 gold

任何检索质量指标，本质都是「检索器的答案 vs 标准答案」的对照。代码把这两者定义得非常干净（eval/metrics.py:3-6）：

  • ranked_ids：检索器按相关性降序返回的 chunk id 列表——这是「考生的答卷」。
  • gold_ids：该 query 应该召回的 id 集合（无序）——这是「标准答案」，也就是 gold。

指标函数做的事，就是把答卷拿到标准答案上比对。以 Recall@K 为例（metrics.py:16-24）：

# Recall@K：前 K 个结果里，命中 gold 的数量 ÷ gold 总数
def recall_at_k(ranked_ids, gold_ids, k):
    if not gold_ids:
        return 1.0                       # gold 为空 → 无可召回，视为满足（避免除零）
    hits = sum(1 for rid in ranked_ids[:k] if rid in gold_ids)
    return hits / len(gold_ids)      # 命中数 / gold 总数

看这行 if rid in gold_ids 就懂了：gold 就是那把「算不算命中」的尺子。检索器返回的 id 只有落在 gold 集合里才计数。

2 · gold 从哪来？——本项目是「构造式 gold」，不是纯人工标注

指南里说「人工标注」是通俗说法，强调它是可信的标准答案。但在 NanoScope 的评测里，gold 是用代码构造 + 埋点出来的，比人工标注更严谨、可复现。看 rag/sweep.py:89-97 造数据时怎么埋 gold：

# 造一批「量子加密」机密 chunk，属于 proj_a —— 这些就是 gold 全集
gold = []
doc_a = store.register_document(admin, title="A组机密")
for i in range(n_per_group):
    rec = store.add_chunk(admin, ..., content=f"量子加密算法密钥分发内部方案第{i}节…",
                          scope=SCOPE_PROJECT, acl_group="proj_a")
    gold.append(rec.id)         # ★ 写入时就登记：这些 id 是「量子加密」query 的标准答案

换句话说：造数据的人一边写 chunk、一边记下「这条应该被『量子加密』这个 query 召回」，把它的 id 塞进 gold 列表。查询时检索器返回的结果，就拿这个 gold 去判分。

🎯 类比：gold 就像老师出题时同时写好的标准答案。学生（检索器）交卷（ranked_ids）后，老师逐题对标准答案打勾——打勾数 ÷ 标准答案总数 = Recall。没有标准答案，卷子根本没法批。

3 · 还有个「反面标尺」：forbidden

这套评测的精妙处在于——除了 gold（该召回的），还埋了 forbidden（越权、绝不该召回的，sweep.py:98-106）：proj_b 的机密 chunk，内容关键词和 gold 高度重合（都含「量子加密」），语义上是最近邻。这样才能证伪隔离：无授权时它必进候选（说明确实难挡），有授权时它被授权 WHERE 拦掉（说明隔离生效）。gold 量「召回够不够」，forbidden 量「隔离漏不漏」——两把尺子，一正一反。

收口：gold = 对某 query 预先认定的「正确答案 chunk id 集」，是所有召回指标的判分标尺。本项目用构造式 gold（造数据时埋点，sweep.py），比人工标注更可复现；并配一个 forbidden 反向集合来证伪隔离。
Q2 MRR = 第一个正确答案名次的倒数，那为什么要求「重排后 nDCG/MRR ≥ 重排前」？MRR 不是越大越好吗？
你没理解错，MRR 确实越大越好。「重排后 ≥ 重排前」不是在说「MRR 越小越好」，而是一条验收断言（assertion）：它要求「重排这道工序不能帮倒忙」——加了 rerank 之后的分数，必须 ≥ 不加 rerank 的分数。这里的 ≥ 比较的是「同一指标的两个版本（重排前 vs 重排后）」，不是指标本身的优化方向。

1 · 先分清两个「大小」，别混为一谈

比较含义方向
MRR 本身越大 = 第一个正确答案排得越靠前越大越好（你说得对）
重排后 MRR vs 重排前 MRRrerank 这道工序有没有把排序改好要求「后 ≥ 前」＝这道工序至少没变差

关键在于 rerank.py:5 那句话的语境——它是在给 rerank（重排序）模块立验收标准：

# rerank.py:5
# 在自建 gold 上证明「重排后 nDCG/MRR ≥ 重排前」（D5/M18.3）

rerank 是检索的第二道工序：第一道（召回）先粗粗捞回一批候选并给个初排；rerank 再用更精细的模型把这批候选重新排一次序，力图把最相关的顶到最前。

2 · 为什么要立这条「≥」断言？——防止重排帮倒忙

重排是个「可能变好、也可能变坏」的操作。它用更贵的模型重新打分，理论上更准，但也可能：

  • 模型选得不好，把本来排第 1 的正确答案挤到第 3 → MRR 从 1.0 掉到 0.33；
  • 过拟合某种模式，在你的真实数据上反而更差。

所以必须有一条底线断言守住：「你这道重排工序，加了之后不许比不加更差」。用公式表达就是：

MRR重排后  ≥  MRR重排前   且   nDCG重排后  ≥  nDCG重排前

这不是「希望 MRR 小」，恰恰相反——正因为 MRR 越大越好，我们才要求「重排只能让它更大或持平，绝不能让它变小」。这是一条单调不降的质量门禁。

🔧 类比：rerank 就像给照片加一道「AI 增强滤镜」。滤镜当然是为了更好看（MRR 更大），但你得有个验收标准：「加了滤镜的照片，不许比原图更丑」。这句话不是说「照片越丑越好」，而是「这道增强工序不许帮倒忙」。「重排后 ≥ 重排前」就是这个意思。

3 · 顺带：MRR 与 nDCG 为什么一起看

两者都衡量「排序好不好」，但侧重不同（metrics.py:27-51）：

指标公式核心侧重
MRR1 / 第一个命中的名次只看第一个正确答案排多前（适合「找一条就够」的场景）
nDCG@KΣ 命中项 1/log₂(名次+1) ÷ 理想排序看所有正确答案的整体排布（越靠前贡献越大）

用两个指标同时立「≥」断言，是为了防「按下葫芦浮起瓢」——重排不能为了顶高第一名（MRR）而把其他正确答案全压下去（nDCG 掉）。两个都不许降，才叫真的没帮倒忙。

收口：MRR 确实越大越好；「重排后 ≥ 重排前」是给 rerank 工序立的单调不降门禁——比较的是「同一指标的重排前后两个版本」，要求重排至少不劣化。它恰恰建立在「MRR/nDCG 越大越好」之上，而非否定它。
Q3 ingest.py 的切割是两种模式：固定+重叠 / 结构段落感知。这是不是偏简单的版本？还有什么方法？
是的，当前是「够用的基线版」，而且代码自己就坦白了这一点。ingest.py:45 注释明写：「模拟『按标题/段落切』的结构感知策略；真实解析器（Markdown/PDF 标题树）留待接入」。业界 chunking 是一条从「字符切」到「语义切」再到「层级切」的谱系，NanoScope 落在最稳的前两档，把复杂度留给了后续接入点。

1 · 当前两种切法（基线）

为什么用「字符」而非「词」切？注释点明（ingest.py:19）：以字符为单位对中文友好，无需引入分词器——这与记忆检索用 trigram 的思路一脉相承（都在回避「中文分词」这个麻烦）。而且配置错误（size≤0 或 overlap≥size）是 fail-closed 抛错，不静默退化，符合项目一贯审美。

3 · 为什么 NanoScope 现在只做前两档？——刻意的工程取舍

  • 符合项目定位：RAG 是「按需可插拔的正交优化」（见 0724 篇 Q12）。chunking 是可替换组件，先用零依赖、确定性的基线跑通端到端隔离与评测闭环，把「更聪明的切法」留作接口。
  • 避免过早优化：⑤⑥ 在切分时就要跑 embedding / LLM，成本高、不确定性大；在记忆规模未到拐点时，收益未必覆盖复杂度（与「BM25 是否必要」同款判断）。
  • 接入点已留好：ingest_document(strategy=...) 用字符串分派策略（ingest.py:77-82），新增 strategy="markdown_tree" 只需加一个分支，不动上下游契约——这就是「留待接入」的落点。
收口：当前两种切法是确定性、零依赖、CJK 友好的基线，代码已坦白「真实解析器留待接入」。业界更进阶的有递归字符、结构树、语义切分、命题切分、父子检索等。NanoScope 先做前两档，是「先跑通闭环、把复杂度留给接口」的刻意取舍，而非能力缺失。
Q4 为什么切片写入 store 需要 SecurityContext？它不是用户发请求时才生成的吗？外部知识库文档的 ctx 从哪来？
因为写入时必须回答「这批 chunk 属于谁、哪个组能看」——而归属绝不能让文档内容或模型自己说了算，只能由可信的运行时上下文注入。你的直觉对了一半：面向用户请求的 ctx 确实在收到消息时生成；但 ingestion 是另一条独立入口，它的 ctx 由发起入库的那个主体提供——可能是管理员、运维脚本、或后台同步任务的系统身份，不来自聊天消息。

1 · 为什么写入非要 ctx 不可——归属标签的唯一可信来源

回顾 Q12/store 的隔离设计：每条 chunk 落库时必须带 tenant / scope / owner_id / acl_group 四个归属标签，可见性 WHERE 全靠它们。问题来了——这些标签谁来填？ 代码给出斩钉截铁的答案（ingest.py:6-7、store.py:89）：

# ingest.py:6-7 —— 红线
# chunk 的 tenant/scope/owner/acl 标签由调用方（运行时上下文）注入，
# ingest_document 只透传给 add_chunk，模型/文档内容无法伪造归属。

# store.py:89
# add_chunk 从 SecurityContext + 显式 scope/acl_group 注入归属，模型无法伪造。

这就是要 ctx 的根本原因：tenant_id 从 ctx.tenant_id 取，绝不从文档正文或函数参数里让人随意指定。否则一份恶意文档只要在正文写「我属于 org 全员可见」，就能把自己提权成全员可见——归属一旦可伪造，整套隔离墙就废了。ctx 是归属的唯一可信来源，这是 fail-closed 原则在写入侧的落地。

🏷️ 类比：ingestion 像往档案库归档文件。每份文件必须贴「密级 + 归属部门」标签，而这个标签只能由持证的档案管理员（ctx）来贴，绝不能让「文件自己封面上写什么就是什么」。否则谁都能伪造一份「绝密→改成公开」的封面蒙混过关。

2 · 那外部知识库文档的 ctx 从哪来？——不来自聊天，来自「入库主体」

关键认知纠偏：SecurityContext 不是「只有用户发消息才会生成」，而是「任何需要鉴权的操作都要带的身份凭证」。用户请求是其中一条来源，但不是唯一。ingestion 是一条独立的管理入口，它的 ctx 由发起入库者提供。项目里就有现成例子——评测造数据时用一个管理员身份入库（sweep.py:84-88）：

# sweep.py:84-88 —— ingestion 用的是「构造出来的管理员 ctx」，不是聊天消息里的
admin = SecurityContext(
    tenant_id="orgX", principal_id="orgX:feishu:admin",
    session_key="feishu:admin", audience_type=AUDIENCE_DM,
    roles=("proj_a", "proj_b"),   # 管理员可跨组入库
)
doc_a = store.register_document(admin, title="A组机密")   # 用这个身份归档

真实生产里，这个入库 ctx 的典型来源有三类：

入库场景ctx 从哪来身份性质
管理员在后台上传部门知识库管理员登录态 → 构造其 SecurityContext真人管理员
定时同步 Confluence/Drive 等外部源后台任务的服务账号（service account）身份系统身份（非自然人）
用户在会话里上传文件（见 Q5）复用该用户请求的 RequestContext发起上传的用户本人

所以「ctx 从哪来」的答案取决于是谁在入库：管理员入库→管理员身份；后台同步→服务账号身份；用户上传→用户自己的请求上下文。无论哪种，都必须有一个可信主体为这批文档的归属背书，这正是写入需要 ctx 的意义。

收口：写入要 ctx，是因为归属标签（tenant/scope/owner/acl）只能由可信运行时身份注入、绝不许文档或模型伪造（fail-closed）。ctx 不是「只有用户请求才有」——ingestion 是独立入口，其 ctx 来自入库主体：管理员、服务账号或（用户上传时）用户自己的请求上下文。
Q5 RAG 的各类文档是用户手动上传的吗？通过请求窗口上传文件，还是什么渠道？
都可以，取决于文档的 scope。NanoScope 当前代码里，文档入库统一走 ingest_document() 这个编程入口（还没有做「聊天窗口拖拽上传」的 UI）。但从架构设计看，三种 scope 的文档天然对应三条不同的入库渠道。「用户在对话里上传文件」只是其中一条（对应 user/DM scope），而且当前尚未接入 UI，是留待接入的能力。

1 · 当前代码事实：只有一个编程入口 ingest_document

先说 ground truth——翻遍 rag/，文档进库的唯一函数是 ingest_document(store, ctx, *, title, text, scope, acl_group, strategy…)（ingest.py:60）。它接收已经是纯文本的 text，负责切块 + 带 ACL 落库。也就是说：

  • 当前没有「聊天窗口点击上传 → 自动解析 PDF/Word」的完整链路，那属于 ingest.py:45 说的「真实解析器留待接入」。
  • 现在调用它的地方是评测 / 造数据脚本（如 sweep.py），由代码显式喂文本和身份。

2 · 架构意图：三种 scope → 三条渠道

Q6 图遍历是把向量建成一张图吗？Pre-filter 先筛再算相似度会丢掉 ANN 加速——为什么不能筛完再图遍历用上 ANN？暴力算余弦不就完全没用到 ANN 了吗？
你的直觉完全正确，而且你亲手推出了本项目的「选定解」！①「图遍历」确实是把向量建成一张图（HNSW）再在图上跳着找近邻。②「筛完再图遍历」这条路真的存在、真的能用上 ANN——它就是三策略里的第三种 Partitioned（分区索引），也正是 NanoScope 最终选定的方案。③ Pre-filter 暴力算余弦确实没用到 ANN，但它被刻意保留为「正确性基线 / recall 天花板」。你没有想错，只是「筛完再建图」这件事有个前提——筛的维度必须能预先分区。

1 · 先确认：「图遍历」是什么

对，就是把向量建成一张图。这里的图是 HNSW（Hierarchical Navigable Small World，分层可导航小世界图）——业界最主流的 ANN 索引（index.py:41 用的 hnswlib）。它把每个向量当作图上一个节点，节点间连「距离近」的边，查询时从入口点沿边贪心跳跃，像走小世界网络一样几跳就逼近最近邻。

  • 暴力搜（brute force）：拿 query 和全部 N 个向量逐个算余弦，O(N)，精确但慢。代码里是 _brute_topk（index.py:65）。
  • ANN 图遍历：在 HNSW 图上跳，只碰 O(log N) 量级的节点就找到近似最近邻，快几个数量级，代价是「近似」（极小概率漏掉真最近邻）。

所以你说的没错：「暴力算余弦」就是彻底不用 ANN；「图遍历」才是 ANN 的加速所在。冲突的根源是——ANN 图是预先对全体向量建好的，而权限过滤要求只在「可见子集」里搜，两者时间轴上打架。

3 · 你的问题正中要害：为什么 Pre-filter 不能「筛完再图遍历」？

因为 HNSW 图必须预先建好，而 pre-filter 的「可见子集」是查询时才知道、且每个用户都不同的。你不可能为「张三这次查询恰好可见的这批向量」现场建一张 HNSW 图——建图本身就是 O(N log N) 的重活，比你省下的搜索时间还贵。所以 pre-filter 一旦筛出子集，只能对这个临时子集暴力算余弦：

Pre-filter：可见子集是「查询时才定、人人不同」→ 无法复用预建图
全体向量（预建了一张 HNSW 大图）
▼ 用户查询到来，WHERE 筛出「他可见的那批」
可见子集：每个用户不同、每次不同 → 大图的边大多指向「被筛掉的点」，图残破无法用
▼ 现建图太贵（O(N log N)）
只能：对可见子集暴力算余弦 O(可见数)

这就是「pre-filter 丢掉 ANN 加速」的精确原因：不是不想用 ANN，是可见子集的动态性让「预建图」无法复用。所以它被定位成「recall 天花板与正确性基线」（index.py:16：pre-filter 永远暴力，不接 ANN）——它的价值是「绝对正确、可复现」，用来给其他策略当参照系。

4 · 你设想的「筛完再图遍历」= Partitioned，本项目的选定解！

你的直觉——「筛完再图遍历不就能用 ANN 了」——是对的，关键在于「什么时候筛」。Pre-filter 是查询时筛（太晚，图建不了）；而 Partitioned 是建索引时就按 ACL 组把向量分好区、每组各建一张 HNSW 子图（index.py:269-279）：

# index.py:269-279 —— PartitionedSearcher（选定解）
# 分区结构：{(tenant,org):大图, (tenant,project,组):子图, (tenant,user,人):子图}
# 查询时：用户可见分区 = 同租户 org ∪ 其 DM 个人分区 ∪ 其所属 project 子图
# 只在这几个分区跑 ANN，结果合并。越权子图【从未被加载/访问】(F3)。
🗂️ 类比：与其把全公司文件堆成一座山、每次查完再挑出「你能看的」（post-filter，越权文件已翻过），或每次现从山里抽出你能看的一小堆逐份翻（pre-filter，暴力）；不如一开始就按部门把文件分成一个个上锁的档案柜，每个柜内部单独编好索引。张三来查，只开他有钥匙的几个柜、在柜内索引上快速定位（子图内跑 ANN）——别的柜从头到尾没打开过。这就是 Partitioned。

它为什么能成立？关键前提在 index.py:277：本项目 ACL 维度是 org/project（部门/项目，数量级几~几十），分区数天然可控——所以「按组预分区建子图」可行。这正是「敢选分区索引」的答辩点。它还留了 fail-safe（index.py:282-283）：分区数异常膨胀超过 256 时，自动退化为 pre-filter 暴力，正确性永远保底。

Q7 给我介绍一下 HNSW。
一句话：HNSW（Hierarchical Navigable Small World，分层可导航小世界图）是当前最主流的 ANN（近似最近邻）索引。核心思想两句话：①把向量连成一张「近的相连」的图，查询时沿边贪心跳跃逼近目标，把 O(N) 暴力降到 O(log N)；②叠成多层（上稀疏、下稠密），像坐「高速→省道→小路」逐级逼近，避免陷入局部最优。NanoScope 用的就是它（index.py:41 的 hnswlib，space="cosine"）。

1 · 要解决的问题：暴力搜太慢

向量检索的本质是「给一个 query 向量，从 N 个向量里找最相似的 top-k」。最朴素的办法是暴力：和全部 N 个逐一算余弦，O(N)。N=一千还行，N=一千万就卡死。ANN 的思路是用一点点精度换巨大的速度——不保证找到「绝对最近」，但以极高概率找到「几乎最近」，代价从 O(N) 降到 O(log N) 量级。HNSW 是 ANN 家族里综合最优的一种。

2 · 两个关键词拆开讲

① Small World（小世界图）——为什么能「几跳就到」

「小世界」就是六度分隔那个现象：社交网络里任意两人平均只隔几个人。HNSW 把每个向量当成图上一个节点，给每个节点连若干条「距离近」的边（邻居）。查询时从某个入口点出发，每一步都跳到「当前邻居里离 query 最近的那个」，像贪心爬山一样逼近目标。因为图有小世界性质，几跳就能从图的任意角落逼近目标区域，不用遍历全部节点。

② Hierarchical（分层）——为什么要叠好几层

单层小世界图有个毛病：可能在一个局部区域里「打转」，跳不出去。HNSW 的解法是叠成金字塔式的多层：

HNSW 多层结构：从稀疏高层逐级下沉到稠密底层
Layer 2（最稀疏，少数节点，长边）——「高速公路」，一跳跨很远
▼ 在本层贪心逼近后，下沉一层
Layer 1（中等密度）——「省道」，中等粒度逼近
▼ 继续下沉
Layer 0（最稠密，全部节点都在）——「小路」，精细定位最终 top-k

查询从最高层的入口点开始，在稀疏图上大步逼近；到某层局部最优后下沉一层，在更密的图上继续精修；一路降到第 0 层（含全部节点）做最终精确逼近。这就像找地址：先上高速到城市，下省道到城区，再走小路到门牌——逐级缩小范围，避免在小路上从头开始瞎找。

3 · 三个必须知道的超参（NanoScope 的取值）

代码里三个默认超参（index.py:83-86）正是 HNSW 的三个旋钮：

超参代码默认含义调大的影响
M16每个节点连多少条边（邻居数）图更密 → 召回更准，但内存更大、建图更慢
ef_construction200建图时每步考察的候选邻居数建的图质量更高，但建图更慢
ef_search50查询时维护的候选队列长度召回更准，但单次查询更慢

本质都是「精度 vs 速度/内存」的权衡旋钮。M 和 ef_construction 在建图时定死，ef_search 可以在查询时动态调（index.py:118 的 set_ef）。

4 · NanoScope 怎么用 HNSW——两个关键约束

  • 只给候选，不做精排（index.py:91-95）：_HnswIndex 只负责「返回近邻的原始下标」，拿到候选后外层再用精确余弦重打分（_brute_topk）。所以先用 ANN 多召回 top_k×4 个候选（_ANN_FANOUT_MULT=4），再精排回 top_k——ANN 只决定「看哪些」，精确余弦决定「怎么排」，保证同一候选集结果可复现。
  • 单线程建图保证可复现（index.py:114-116）：num_threads=1，因为多线程插入顺序不确定会让图结构不可复现——这是项目「确定性」审美的体现。
  • 可选依赖 + 优雅降级（index.py:40-48）：没装 hnswlib 时全部退化为纯 Python 暴力余弦，SearchOutcome 契约逐字节不变——HNSW 是加速层，不是正确性的必需品。
⚠ 红线：HNSW 永不承担可见性判断（index.py:22-24、index.py:94-95）。它只做「候选召回排序」，可见性永远由授权 WHERE 或分区结构保证。这就是为什么 Q9 里 visible_chunks 依然不可省——下一问详解。
收口：HNSW = 分层小世界图的 ANN 索引，用「多层图 + 贪心跳跃」把最近邻搜索从 O(N) 降到 O(log N)，靠 M / ef_construction / ef_search 三个旋钮权衡精度与速度。NanoScope 用它只做候选召回（外层精确余弦重排），单线程建图保证可复现，且未装依赖时优雅降级为暴力——它是可选加速层，永不碰可见性。
Q8 我们这里 RAG embedding 的向量是多少维的？

1 · 证据：维度由 embedding 模型决定

向量维度不是我们随便定的，而是由所选 embedding 模型决定。NanoScope 的选型写死在 embedding.py：

# embedding.py:38-39（GlmEmbedder 类 docstring）

所以：不传 dimensions（默认 None）→ 每条文本被编码成一个 2048 维的稠密浮点向量。

2 · 降维是可选优化

GlmEmbedder 构造时可传 dimensions（embedding.py:47），非 None 时会加进请求 payload（embedding.py:60-61），让 GLM 直接返回降维后的向量：

dimensions 取值输出维度权衡
None（默认）2048信息最全，精度最高；存储/计算成本最大
1024 / 512（示例）对应值省一半以上存储、检索更快；轻微精度损失

为什么降维有用？2048 维向量存 100 万条 = 约 2048×4字节×1M ≈ 8 GB；降到 512 维直接省到 2 GB。对大规模库，降维是很实际的成本优化——这也是 GLM embedding-3 相比固定维度模型的一个灵活点。

3 · 维度在检索链路里怎么流转

  • 建 HNSW 图时：维度自动从向量读取（index.py:108 self._dim = len(vecs[0])），传给 hnswlib.Index(space="cosine", dim=self._dim)。所以换维度不用改索引代码，自适应。
  • 算相似度时：用余弦相似度（index.py:56-62 _cosine），维度多少都通用。
  • 测试时：可注入 FakeEmbedder（确定性假向量，embedding.py:12），维度可控，不依赖网络/密钥——这就是为什么单测不需要真调 GLM。
⚠ 一致性铁律：建库和查询必须用同一个 embedding 模型 + 同一维度。若入库时用 2048 维、查询时用 512 维，两者根本不在同一向量空间，余弦相似度完全无意义。这是所有向量检索系统的隐性前提。
收口：RAG embedding 用 GLM embedding-3，默认 2048 维（embedding.py:24,38-39）；支持传 dimensions 降维（如 1024/512）以省存储、加速。维度自动流入 HNSW 建图与余弦计算，测试用 FakeEmbedder 解耦。铁律：建库与查询必须同模型同维度。

3 · 为什么索引不可尽信？——三个现实风险

  • 陈旧（staleness）：分区索引是建索引时的快照（index.py:320-342 靠 revision 判断是否重建）。若某 chunk 的权限刚被调整、而索引还没重建，索引里就是过期视图。SQL 查的是实时当前状态。
  • 误配（misconfiguration）：分区 key 的推导（index.py:307-312）若有 bug、或 use_ann 开关配错，可能把某 chunk 分错区。索引出错，WHERE 兜底。
  • 召回近似性：ANN 本就是「近似」，加上 fanout 放大召回，候选集里可能混入本不该出现的项。交集是确定性的最后一道闸。
🔐 类比：分区索引像大楼里的「楼层门禁」——刷卡只让你进你那层，很快很方便。但真正的机密档案柜上还有一把独立的锁（visible_chunks）。就算门禁系统被改错了、放你进了别的楼层，档案柜的锁依然打不开。门禁负责效率，柜锁负责安全——你不会因为有了门禁就把柜锁拆了。

4 · 这正是项目「隔离墙与检索正交」审美的落地

这个设计呼应了 0724 篇反复强调的原则：可见性（安全）与检索排序（性能）解耦。

  • 索引可以大胆优化：换 HNSW 超参、改分区策略、上更激进的 ANN——永远撞不穿隔离墙，因为最终有 SQL 交集兜底。
  • 安全不依赖索引正确：即便索引层完全失效（退化暴力、甚至召回全库），visible_chunks 交集仍保证只返回可见项。这就是 fail-closed：出错时向「更安全」的方向塌缩。
  • 可证伪：正因为有权威的 visible_chunks，才能拿它当基准，检验索引层有没有「扩大权限」（forbidden_doc_exposure 应恒为 0，search.py:78-85）。
收口：分区建子图是加速层的近似隔离（可能陈旧/误配/近似），visible_chunks 是数据库层的授权真值。search.py:56 用「索引候选 ∩ SQL 白名单」把两者串成纵深防御——索引负责快，WHERE 负责对。省掉 visible_chunks 就等于把安全押注在「索引永不出错」上，违背 fail-closed。这正是「隔离墙与检索正交」的核心落地。
Q10 这里 rerank 用什么算法？除此之外还有哪些常见的算法？
一句话：当前用的是一个确定性 StubReranker（占位版），不是真模型。它用「query 与 chunk 的字符级重合度」（Jaccard 变体）当相关性分（rerank.py:23-43），对 CJK 友好、可离线复现。代码明说「真实 cross-encoder（如 bge-reranker）留待接入」（rerank.py:3-5），这个 stub 只为在合成 gold 上跑通「重排后 nDCG/MRR ≥ 重排前」的验收管线。

1 · 先分清：rerank 在链路里是「第二道排序」

检索通常是两阶段：①召回（retrieve）——用快而糙的方法（BM25/向量 ANN）从海量库里粗筛出 top-N 候选；②重排（rerank）——用慢而精的模型只对这 N 个候选重新精排，把最相关的顶到最前。为什么不直接用精模型搜全库？因为精模型太贵，只能用在「已缩小到几十个候选」的小集合上。这就是 rerank 的定位。

2 · NanoScope 当前的 StubReranker

# rerank.py:24-42 —— 确定性 stub：字符级重合度当联合分
def rerank(self, query, candidates):
    q = set(query.strip())                        # query 的字符集合
    scored = [
        (idx, len(q & set(text)) / len(q))        # |交集| / |query 字符数|
        for idx, text in enumerate(candidates)
    ]
    scored.sort(key=lambda kv: (-kv[1], kv[0]))  # 分高在前，同分按原序（确定性 tie-break）
    return [idx for idx, _ in scored]
  • 算法本质：|query字符 ∩ chunk字符| / |query字符|——一个 Jaccard 变体，衡量「query 的字覆盖了多少」。
  • 为什么用它：零依赖、确定性可复现、对中文友好（按字符不按词）。它不是真语义模型，但足以演示「重排管线 + 增益度量」是否跑通。
  • 可整体替换：Reranker 是个 Protocol（rerank.py:16-20），只要实现 rerank(query, candidates)->list[int]，真实模型可无缝替换 stub，契约不变。
⚠ 红线（rerank.py:7）：rerank 只对已隔离的可见候选排序，绝不改变可见性。它拿到的候选早已过了 visible_chunks 授权白名单——重排纯粹是「排序美化」，动不了权限。

为什么 Cross-Encoder 是当前主流？——和召回用的 Bi-Encoder 对比

  • Bi-Encoder（召回用，如 embedding 模型）：query 和 doc 各自独立编码成向量，再算余弦。可以预先算好 doc 向量入库，检索时只编码 query——快，适合搜全库，但 query 和 doc「没见过面」，精度受限。
  • Cross-Encoder（重排用）：query 和 doc 拼在一起送进模型，让二者在每一层充分交互——精度高得多，但不能预计算（每个 query×doc 都要现算一次），只能用在「已缩小到几十个候选」的重排阶段。

这正好解释了两阶段设计：Bi-Encoder 快而糙负责召回，Cross-Encoder 精而慢负责重排——各司其职。NanoScope 注释点名的 bge-reranker 就是典型的开源 Cross-Encoder，是 stub 未来的替换目标。

收口：当前 rerank 是确定性 StubReranker（字符级 Jaccard 重合度，rerank.py），零依赖可复现，仅为跑通验收管线；真实 Cross-Encoder（bge-reranker）留待接入。业界谱系：字面重合 → Learning-to-Rank → Cross-Encoder（当前主流） → LLM-as-Reranker。核心分野是「Bi-Encoder 召回、Cross-Encoder 重排」的两阶段分工。

Q12 形象讲讲 HNSW 一次 query 怎么维护候选队列？为什么 ANN 召回 top_k×4 个候选，再用余弦决定？召回过程不是已经算过 cos 了吗？
两句话：①HNSW 查询时靠两个队列在图上「贪心找路」——一个 candidates（待探索，离 query 越近越先弹）、一个 W（当前找到的最好 ef 个，动态最近邻表）；它只走图的一小条路，算过的 cos 只是「导航用」的、且只算了走过的那几十个点。②正因为它是近似且只探了局部，代码把 ANN 结果当「粗筛候选池」——多捞 top_k×4 个，丢掉 HNSW 自己那套距离（index.py:125 的 labels, _），再用一把统一的精确余弦在这几个候选里重新算、重新排（index.py:148-152）。所以不是「算了两遍」，而是「导航用的近似分」和「定序用的精确分」是两码事。

1 · 先建立画面：HNSW 查询时维护哪两个队列

在最底层（layer 0）真正找近邻时，HNSW 同时维护两个优先队列（ef 就是 ef_search=50，队列容量）：

3 · 回答你的核心疑问：召回时不是已经算过 cos 了吗？为什么还要再算？

先看这段代码里最关键的一个细节——HNSW 算出的那套距离，被当场扔掉了（index.py:120-128）：

def query(self, query_vec, k):
    ...
    labels, _ = self._index.knn_query(...)   # ★ 只要 labels（下标），距离 _ 直接丢弃

然后外层拿这些下标，多捞一批、再用一把统一的精确余弦重新打分排序（index.py:148-152）：

所以你的直觉「召回时不是算过 cos 了吗」——对，但那笔 cos 有两个『不能用来定序』的毛病：

#毛病后果重打分怎么修
①近似：HNSW 只探了图的一条路，走过的点才算过 cos，真近邻可能在没走到的分支里被漏掉直接拿 HNSW 的 top-5 当答案，可能少 1~2 个真正最相关的先多捞 4 倍（20 个）撒大网，把真近邻「大概率也网进来」，再精算挑真 top-5 → 补 recall
②不可复现：图遍历路径、内部浮点、库版本都可能让同一 query 的近似分/顺序有微差同样输入两次跑，结果可能不逐字节一致——破坏项目的 D4 一致性红线丢掉 HNSW 的分，改用外层唯一一把精确 _cosine + 确定性 tie-break (-score, id)（index.py:79）→ 逐字节可复现

代码注释把这层意思说得很直白（index.py:141-142）：「ANN 只影响『看哪些候选』，不影响『候选内如何排序/过滤』，故同一候选集下结果逐字节可复现」。换句话说，职责被干净地劈成两半：

近似分 vs 精确分：一次检索里两笔 cos 的分工
① HNSW 内部的 cos（导航分）：只为「在图上往哪跳、留哪 20 个候选」服务 → 用完即弃
▼ 交出的只有 20 个「候选下标」，不含任何分数
② 外层 _brute_topk 的 cos（定序分）：在这 20 个候选上精确重算，决定最终 top-5 的名次与去留（min_score）

4 · 为什么偏偏是「×4」？多捞多少才够？

_ANN_FANOUT_MULT = 4（index.py:88）是个召回-开销的折中旋钮：

  • 捞太少（=top_k）：网太小，ANN 一漏近邻就补不回来，recall 掉。
  • 捞太多（=全库）：等于退化成暴力搜索，ANN 加速全废。
  • ×4：要 5 个先看 20 个。撒 4 倍大的网，真近邻落进候选池的概率大幅提升，而精确重打分只在这 20 个上算——O(fanout) 而非 O(N)，加速仍在。这就是「用一点点多余的精算，把 ANN 的近似误差买回来」。

注意 min(len(corpus.chunks), max(top_k*4, top_k)) 的封顶：候选池永远不超过语料总数，小语料时自然收敛到「全量精算」，等价于暴力基线——小数据不冒险，大数据才吃 ANN 红利。

🎣 类比：撒网捕鱼再上岸挑。HNSW 像凭鱼群探测仪（近似）在大海里快速圈一片鱼多的水域，一网下去捞 20 条——探测仪只告诉你「这片有鱼」，不保证每条都大。上岸后你用秤（精确余弦）逐条称重，挑出最大的 5 条，还把太小的（min_score）扔回海里。探测仪的读数（HNSW 距离）只用来决定「在哪撒网」，上不了餐桌；真正定夺去留的是岸上那杆统一的秤。多捞到 20 条（×4）就是怕探测仪不准、5 条里混进小鱼。
⚠ 一句话戳破误区：「召回时算过 cos」和「重打分算 cos」不是重复劳动——前者是 HNSW 为了在图上导航顺带算的、只覆盖走过的几十个点、且用完丢弃；后者是在选定的候选池上，用项目唯一权威的那把余弦尺做最终定序与过滤。近似分负责「快而广地找候选」，精确分负责「准而稳地定名次」，各司其职。
收口：HNSW 查询 = 上层高速贪心下降（ef=1）+ 底层 ef=50 双队列（candidates 探路、W 存最好）展开，只对走过的几十个点算 cos，天生近似。故 NanoScope 把 ANN 当「粗筛」：多召回 top_k×4、丢掉 HNSW 自带距离（labels, _），再用外层唯一一把精确余弦 + 确定性 tie-break 在候选池里重排（_brute_topk）。两笔 cos 分工明确：导航分求快、定序分求准且可复现——这既补回了近似召回的 recall，又守住了 D4 逐字节可复现红线。
Q13 过程中文档可能被修改，索引会自动重建吗？
会——但不是「立刻重建」，而是「下一次查询时按需、惰性重建」。机制是一个全库单调递增的版本号（revision）：任何写入都把它 +1（store.py:180）；PartitionedSearcher 缓存自己建索引时的版本号，每次 search() 开头先比一次版本（index.py:359 → _refresh_if_stale），发现「库变了、我旧了」就整体重建分区索引再查。重要澄清：当前 store 只有 add_chunk（追加写），没有原地改/删的方法——所以今天说的「文档被修改」，实现层面是「以新 chunk 再入库」，同样触发 revision +1、同样被自动重建捕获。

1 · 触发信号：一个全库共享的 revision 计数器

索引怎么知道「库变了」？靠的不是监听文件、也不是定时轮询，而是 DB 里一行单调递增的版本号。建表时初始化为 0（store.py:67），每写一条 chunk 就在同一个事务里 +1（store.py:180）：

    "UPDATE rag_metadata SET value = value + 1 WHERE key = 'chunks_revision'")
self._conn.commit()   # ★ chunk 落库与版本号 +1 原子提交——不会出现「数据变了但版本没变」

revision 作为只读属性暴露（store.py:105-112），读不到就 raise（fail-closed，宁可报错不给陈旧结果）。它是「库内容有没有动过」的唯一权威信号——不关心动了哪条、怎么动的，只要数字变了就代表「你手上的索引可能过期」。

PartitionedSearcher 建索引时把当时的版本号记在 self._revision（index.py:341）。之后每一次 search() 的第一行就是自检（index.py:358-359）：

def _refresh_if_stale(self):

所以「自动重建」的准确含义是：不是写入的瞬间同步重建，而是把重建推迟到下一次真正要查的时候——这叫惰性重建（lazy / on-read rebuild）。好处是：写入侧极轻（只 +1 一个计数器），连写 100 条也不会触发 100 次昂贵重建；重建成本只在「确实有人来查」时付一次。

📚 类比：图书馆的「馆藏版本号」。管理员每上/换一批书，就在门口牌子上把版本号 +1。你（检索器）不必时刻盯着书架，只需每次进门瞄一眼牌子：号没变就用脑子里的旧地图直接找；号变了才花几分钟重新走一遍、更新地图。既不会用过期地图（安全/正确），也不会每上一本书就全馆重绘（高效）。

3 · 重建时的一致性：带「版本前后校验」的重试循环

重建过程本身也可能撞上「边建边被人写」的竞态。_build_partitions 用一个 read-verify-retry 循环兜住（index.py:320-342）：

def _build_partitions(self):
    with self._refresh_lock:                    # RLock 串行化重建，避免并发重复建图
        if self._revision == self._store.revision:
            return                              # 已最新，直接返回
        while True:
            revision_before = self._store.revision      # ① 建之前记一次版本
            buckets = 分桶(self._store.all_chunks_unfiltered())
            partitions = {k: _EmbeddedCorpus(...) ...}  # ② 全量重嵌 + 重建 HNSW 子图
            revision_after = self._store.revision       # ③ 建之后再记一次版本
            if revision_before == revision_after:       # ④ 建的过程中没人写 → 快照一致
                self._partitions = partitions
                self._revision = revision_after
                return
            # 否则：建到一半库又变了 → 丢弃、拿新版本重建，直到拿到一致快照

这段的精髓是「建前建后各读一次版本，相等才采信」：保证落地的索引对应某一个原子快照，绝不会是「一半旧数据 + 一半新数据」的撕裂状态。配合 RLock 串行化，多线程并发查询也只会重建一次。

⚠ 三个必须说清的边界（面试防守点）：
  • 粒度是「全量重建」，非增量。_build_partitions 每次都 all_chunks_unfiltered() 重新分桶、重新 embed、重建所有 HNSW 子图。小语料（本项目 org/project 数量级几~几十）无所谓；真上大规模需换「增量 add_items / 脏分区局部重建」——这是坦白的演进点，非当前实现。
  • 「修改/删除」当前没有原地实现。store 只有 add_chunk（append-only），无 update/delete 方法。所以「文档被修改」today = 重新 ingest 成新 chunk（revision 照样 +1、照样被捕获重建）；真要支持「改一条/删一条」，得先在 store 加相应写口并同样 bump revision，索引侧的 revision 机制无需改动就能自动跟上。
  • 非分区路径（PreFilterSearcher）不缓存、无此问题。它每次查询都现取 visible_chunks 现算，天然永远看到最新数据——「自动重建」只对缓存了 HNSW 子图的 PartitionedSearcher 才是个议题。
收口：会自动重建，走「revision 计数器（写入 +1，store.py:180）→ 查询前惰性自检（_refresh_if_stale，index.py:346）→ 版本前后校验的重试循环全量重建（index.py:325-342）」三步。设计取舍：写轻（只 +1）、读时才付重建成本、快照强一致。两条诚实边界：当前是全量重建非增量，且 store 只追加无原地改删——但 revision 机制对未来接入改/删是前向兼容的（新写口照样 bump，索引自动跟上）。
Q14 补充 reranker 主流模型架构（重点 Cross-Encoder），并梳理本项目 RAG 里 reranker 的数据流全程。
两部分：①主流重排模型 = Cross-Encoder：把 [CLS] query [SEP] doc [SEP] 拼成一条喂进 BERT 类编码器，让 query 与 doc 的每个 token 在自注意力里充分交互，最后一个打分头输出一个相关性标量。它比召回用的 Bi-Encoder（双塔各自编码、算 cos）准得多，代价是不能预计算、每个 (query,doc) 对都要现算一次前向，所以只用在「已缩小到几十条候选」的重排阶段。②本项目当前是 StubReranker（字符级 Jaccard 占位，rerank.py:33-43），但它严格实现了同一个 Reranker 契约、跑的是同一条数据流——接口即真实 Cross-Encoder 的插槽，换模型不动链路。

1 · Cross-Encoder 架构：为什么它准？

要讲清 Cross-Encoder，最好的办法是把它和召回阶段的 Bi-Encoder（双塔）并排看——两者是「检索两段式」的两半：

结构Enc(query)→向量 a；Enc(doc)→向量 bEnc([CLS] q [SEP] d [SEP])→打分头→标量
交互时机编码后才交互（只在最后算一次 cos(a,b)）编码中就交互（每层自注意力里 q↔d 逐 token 互看）

一句话抓住本质：Bi-Encoder 把 query 和 doc「隔空」各编码成向量再比一次，Cross-Encoder 把它俩「贴脸」拼在一起让 Transformer 逐 token 互相看。后者能捕捉「否定、指代、条件、细粒度匹配」这些双塔向量压不进去的信号（例如 query「不含糖的饮料」vs doc「无糖」——双塔容易被「糖」带偏，交叉编码能读懂「不/无」的否定关系）。

Cross-Encoder 打分：一次前向的结构
拼接输入：[CLS] query tokens [SEP] doc tokens [SEP]
▼ 整条序列进 Transformer
多层自注意力：query token ↔ doc token 双向充分交互（这是精度来源）
▼ 取 [CLS] 表示
打分头（Linear→scalar）：输出这对 (query, doc) 的相关性分数
▼ 对候选逐一打分后
按分数降序 = 重排后名次

为什么只能放在重排、不能放在召回？因为它不可预计算：doc 向量没法离线建库，来一个 query 就得把「这个 query × 每条候选」全跑一遍完整前向。对百万级全库跑一遍不现实；但对召回缩小后的几十条候选跑一遍完全可接受——这正是「Bi-Encoder 召回（快而广）→ Cross-Encoder 重排（精而重）」两段式的分工由来，也是本项目 search.py 链路的骨架。

reranker 是 doc_search_visible 的最后一道工序，位于「授权→双路召回→RRF 融合」之后（search.py:69-75）。把整条链拆开看它在哪、拿什么、吐什么：

RAG 检索链里 reranker 的上下游数据流
① 授权过滤：visible = store.visible_chunks(ctx) → by_id = {c.id: c}（search.py:44-47）
▼ 只在可见集合内继续

▼ 两串 id 排名

▼ 下标映射回 id

放大第 ⑤ 步——reranker 内部（StubReranker.rerank，rerank.py:33-43）到底做了什么：

def rerank(self, query, candidates):        # candidates = cand_texts（一串候选正文）
    q = set(query.strip())
    if not q or not candidates:
        return list(range(len(candidates)))  # 退化：原序返回（abstain 友好）
    scored = [
        (idx, len(q & set(text)) / len(q))    # 字符级 Jaccard：query 与候选的重合度
        for idx, text in enumerate(candidates)
    ]
    scored.sort(key=lambda kv: (-kv[1], kv[0]))  # 分数降序，同分按原下标（确定性 tie-break）
    return [idx for idx, _ in scored]        # ★ 只返回「重排后的下标顺序」，不返回文本

三个关键契约点，正是「换成真 Cross-Encoder 也不用改链路」的原因：

  • 入参是纯文本 + query：rerank(query, cand_texts)。真 Cross-Encoder 也正是吃这个——把每个 (query, text) 拼接进 Transformer 打分，接口一字不差。
  • 出参是下标顺序（list[int]）而非文本/分数：由 Reranker Protocol 规定（rerank.py:16-20）。下标让外层用 cand_ids[i] 精确还原 id，reranker 无需知道 id/chunk 结构——职责最小化。
  • 红线：只排序，不碰可见性（rerank.py:7）。它拿到的 cand_texts 早已是「授权 WHERE + ∩by_id」过滤后的可见候选，rerank 只在这个封闭集合内换名次，无论怎么打分都不可能引入越权 chunk。这与 Q9/Q11 的「隔离墙与检索正交」是同一条红线。
🏅 类比：初赛海选 → 决赛评委打分。召回+RRF（Bi-Encoder 那一路）像海选：快速从全库刷掉绝大多数，留 20 强进决赛。reranker（Cross-Encoder）像决赛评委：只对这 20 个选手逐一细看、当场打分重排，选出前 5 名。评委不会去场外再拉人进来（不碰可见性），也不必给全国海选打分（不可预算、只处理决赛候选）——快慢分工、精粗互补。
收口：主流重排是 Cross-Encoder——query×doc 拼接进 Transformer 逐 token 交互、打分头出标量，精度高但不可预计算，故专用于召回后的几十条候选。本项目当前是 StubReranker（字符级 Jaccard，rerank.py:33-43），但严守同一 Reranker 契约：吃 (query, cand_texts)、吐重排下标、只排序不碰可见性。数据流固定为「授权→BM25+向量召回→RRF 融合→取候选文本→rerank 出下标→还原 id 截断 top_k→wrap 注入」（search.py:44-75），真实 bge-reranker 接入时只换第⑤步的实现，全链路一行不改。
Q15 关键内容被切成 chunk1/chunk2，只有 chunk1 分数高进了 prompt、漏了 chunk2——我的项目会有这情况吗？重叠切片能 100% 解决吗？
会，而且重叠切片不能 100% 解决——这是所有 RAG 的固有难题，不是你项目的 bug。你的 chunk_fixed_window 默认 size=200 / overlap=40（ingest.py:16），只在相邻两片的接缝处补了 40 字符的公共区。它能救的只有「关键信息恰好横跨那条切割线、且长度 ≤40 字符」这一种情况；一旦关键信息被拆到两片的非重叠区（间隔 >160 字符）、或分散在文档相距很远的两段，overlap 完全够不着。真正的缓解不是靠 overlap，而是靠「返回多个 chunk（top_k>1）+ 双路召回 + 更聪明的切分/父子检索」组合兜底。

1 · 先算清楚：你的 overlap 到底能盖住多大范围

Q18 HNSW 底层会不会这样：停止时 candidates 里最近的（如 .70）已 < W 里最差的，但这个最近点的邻居其实 > W 里最差的、被漏了？顶层又是怎么用贪心找到最近点的？
你抓到了 HNSW 的命门——是的，完全可能漏，而这正是它叫「近似最近邻（ANN）」而非「精确最近邻」的根本原因。停止条件「candidates 最近的都 ≥（比 W 最差的更远）就停」是一种剪枝赌注：它赌「一个比当前结果都远的点，其邻居也大概率更远，不值得再展开」。这个赌基于小世界图「近邻的近邻仍相对近」的统计规律，大概率成立，但不保证——你说的那种「远点身后藏着近邻」的情况真会发生，就是 ANN 的召回损失。顶层贪心则是另一码事：每层只维护 1 个最近点（ef=1），反复跳到「当前点的邻居里离 query 最近的那个」，直到邻居都不更近为止（爬山法），把这个落点作为下一层入口。

1 · 先正面回答：会漏，这是 ANN 的定义性代价

你描述的场景精确无误。底层展开的停止条件是（回顾 Q12 的循环）：「当 candidates 队列里最近的待探点，都已经比 W 里最差的结果还远时，停」。它的隐含假设是：

剪枝赌注：「既然这个候选点 X 本身都比我现有的 top-ef 都差，那 X 的邻居（离 X 近的点）大概率也在 X 附近、离 query 也远，展开它多半是白费力气——所以直接放弃 X，不看它的邻居。」

但正如你指出的：X 离 query 远，不代表 X 的某个邻居离 query 也远。图上完全可能存在「X 是个远点，但它恰好连着一个离 query 很近的 Y」。一旦到达 X 时触发了停止条件、没展开 X，Y 就永远不会被发现——这就是 ANN 的召回损失（recall loss）。

🏔️ 类比：爬山找最高峰，雾里只看脚下几步。你规定「如果周围能看到的点都比手上记的最高点矮，就收工」。但也许翻过眼前这座矮坡，背后藏着一座更高的山——因为雾太大（只看局部邻居）你没走过去，就把它漏了。HNSW 就是这个「雾里爬山」：快（不用走遍全山），但可能错过被矮坡挡住的高峰。

3 · 顶层贪心：ef=1 的「爬山法」怎么找最近点

你问的第二半——顶层（上面几层稀疏图）是怎么贪心的。它和底层 ef=50 的展开不是一回事：上层只为「快速逼近 query 所在区域」，每层只维护 1 个当前最近点（等价 ef=1），做纯粹的贪心爬山：

顶层贪心爬山（每层 ef=1）：一步步跳向 query
① 从本层固定入口点 cur 出发，算 dist(cur, query)
▼ 看 cur 的所有邻居
② 邻居里挑一个「离 query 比 cur 更近」的，跳过去（cur ← 该邻居）
▼ 重复②
③ 直到「cur 的所有邻居都不比 cur 更近 query」——本层到达局部最近点，停
▼ 把这个落点作为下一层入口，下沉
④ 在下一层（更稠密）重复①~③，越走越精细，最终到 Layer 0 交给 ef=50 精搜

关键点：贪心 = 每步都往「邻居中离 query 最近」的方向走，只要还能更近就继续，一旦周围没有更近的就停在本层。上层图稀疏、边跨度大（长边像高速公路），几跳就能横跨大半张图逼近 query；下沉一层后图变密、边变短，做更精细的逼近。这样避免了在最底层稠密图里从随机点开始一小步一小步挪——分层的意义就在这。

⚠ 顶层贪心也会陷「局部最优」：纯贪心（ef=1）在单层可能卡在局部最近点、错过全局更近的区域。HNSW 的解法正是分层（上层用长边跨越、跳出局部坑）+ 底层加宽 ef（Layer 0 用 ef=50 而非 1，容忍暂时变远的探索）。所以「顶层 ef=1 贪心 + 底层 ef=50 加宽」是一套组合拳：上层求快速逼近、下层求召回质量。
收口：会漏——「candidates 最近的都比 W 最差的远就停」是剪枝赌注，赌「远点的邻居也远」，基于小世界图统计规律大概率成立但不保证，这正是 ANN「近似」的来源。项目用三层兜底把漏概率压低：ef_search=50 加宽、M=16 高连通多路径、外层 fanout×4 多召回 + 精确重排（承认会漏才多捞再精算），并保留 use_ann=False 暴力逃生舱作 recall 天花板。顶层则是 ef=1 贪心爬山：每步跳向「邻居中离 query 更近者」，无更近点即停，落点下沉作下一层入口——分层用长边跳出局部最优，底层加宽 ef 保召回。
