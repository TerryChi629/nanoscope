2 · 两个圈层的分工——Loop vs Runner 是理解全局的钥匙

初学者最容易混淆的就是 Loop 和 Runner 的边界。看它们各自源码文件头一行的 docstring，分工写得非常清楚：

维度Agent LoopAgent Runner
源码 docstring"Agent loop: the core processing engine."（loop.py:1）"Shared execution loop for tool-using agents."（runner.py:1）
关心的东西会话、历史、记忆、压缩、命令、多平台回复——整个回合的产品语义只关心「模型想一步、要不要调工具、调完接着想」——纯执行语义
产物把回复 publish 到 Bus，落库 session返回 AgentRunResult（final_content / messages / usage）
类比项目经理：拉需求、开会、归档、对外汇报干活的工程师：埋头「写代码→跑测试→改」直到通过

Loop 在 _state_run 里调用 _run_agent_loop，后者内部构造 AgentRunSpec 交给 Runner 执行（loop.py:1917-1939）。所以数据流是单向下钻的：Bus → Loop（回合编排）→ Runner（工具循环）→ Providers（LLM）/ Tools（动作）。

M1 Agent Loop（agent/loop.py）—— 核心处理引擎与回合状态机
职责：Loop 是整个 Agent 的常驻主循环——从 Bus 无限取消息，为每条消息编排一个「回合（turn）」。它自己的 docstring 列了五件事：①从 Bus 收消息 ②用历史/记忆/技能建上下文 ③调 LLM ④执行工具 ⑤把回复发回去（loop.py:173-182）。它把一个回合拆成 7 个状态用状态机跑，天生支持「同会话串行、跨会话并发」。

1 · 常驻主循环：run() 的取消息节奏

主循环在 AgentLoop.run（loop.py:1118）。它的骨架是一个 while self._running，每次用 1 秒超时去 Bus 取一条消息——取到就分发，取不到（超时）就顺手做一次「空闲会话压缩」的检查：

# loop.py:1125-1134 —— 主循环的心跳：取消息 or 借空档做空闲压缩
while self._running:
    try:
        msg = await asyncio.wait_for(self.bus.consume_inbound(), timeout=1.0)
    except asyncio.TimeoutError:
        self.auto_compact.check_expired(          # ← 没消息时才跑空闲压缩（M6 详述）
            self._schedule_background,
            self.llm_runtime,
            active_session_keys=self._pending_queues.keys(),
        )
        continue

这个「1 秒超时 + 超时即做后台维护」的设计很关键：它让 Loop 既能实时响应新消息，又能在空闲间隙推进定时任务（空闲压缩、cron），不需要额外线程。consume_inbound 本身是 bus/queue.py:24 的 await self.inbound.get()。

2 · 同会话串行、跨会话并发——并发模型

取到消息后，Loop 不在主循环里同步处理（那样会阻塞后续消息），而是走 _dispatch（loop.py:1261），其 docstring 直接点题："Process a message: per-session serial, cross-session concurrent."。机制是每个会话 key 维护一个 pending 队列：

  • 会话已有在跑的任务：新消息不另起任务，而是 put_nowait 塞进该会话的 pending 队列，做「回合中注入」（loop.py:1177-1204，队列表 self._pending_queues 定义在 loop.py:401）。
  • 会话空闲：为它新建 pending 队列并起一个 asyncio task 跑 _process_message（loop.py:1292 建队列、loop.py:1331 调用）。
🍽️ 类比：一个会话就像餐厅的一桌客人。同一桌的追加点单必须排到这桌的服务流程里（串行，避免上错菜）；但不同桌可以同时服务（并发）。pending 队列就是每桌的「加菜小票夹」。

3 · 回合状态机：一个 turn 的 7 个状态

Loop 把「处理一条消息」抽象成显式状态机，状态枚举在 TurnState（loop.py:103-111）：RESTORE → COMPACT → COMMAND → BUILD → RUN → SAVE → RESPOND → DONE。状态转移写成一张查表（_TRANSITIONS，loop.py:241-250）——每个状态处理函数返回一个事件字符串，驱动器查表得到下一个状态。逐个状态看：

状态处理函数（loop.py）干什么
RESTORE_state_restore :1780取/建 session；恢复上次未完成的 checkpoint 与 pending user turn；抽取消息里的文档/图片（:1799-1802）
COMPACT_state_compact :1816调 auto_compact.prepare_session 拿到「上一段对话的摘要」注入本回合（:1817）
COMMAND_state_command :1821斜杠命令派发；命中即走「shortcut」直接 DONE，不进 LLM（:1840-1857）
BUILD_state_build :1860按 token 预算取历史、拼 initial_messages（system+历史+本轮）、必要时先做一次归并压缩（:1865-1894）
RUN_state_run :1908调 _run_agent_loop 把活交给 Runner（:1917-1939），拿回 final_content/tools_used/stop_reason
SAVE_state_save :1949落库本回合、算延迟、触发容量上限归档与按 token 归并（:1965-1988）
RESPOND_state_respond :1991组装 OutboundMessage（:1995-2003），随后 publish 到 Bus

4 · BUILD → RUN → SAVE 的核心数据流

这三步是回合的「心脏」。BUILD 在 _state_build 里先按上下文窗口算出可回放的历史条数与 token 预算，再取历史、拼消息：

# loop.py:1874-1894 —— BUILD：按预算取历史 → 拼 initial_messages
_hist_kwargs = {
    "max_messages": replay_max_messages,
    "max_tokens": self._replay_token_budget(ctx.runtime),   # 窗口 − 输出预留 − 1024
    "extend_to_user": False,
}
ctx.history = ctx.session.get_history(**_hist_kwargs)          # 从 Session 取裁剪后的历史（M8）
ctx.initial_messages = self._build_initial_messages(       # system prompt + 历史 + 本轮
    ctx.msg, ctx.session, ctx.history, ctx.pending_summary, ...)

RUN 把 initial_messages 交给 _run_agent_loop（它内部再构造 AgentRunSpec 调 Runner，loop.py:1917-1939）；SAVE 则负责把新回合写回 session，并在非临时回合时触发两类压缩收尾（容量上限归档 + 按 token 归并）：

# loop.py:1973-1988 —— SAVE：落库 + 触发压缩收尾
self._save_turn(ctx.session, ctx.all_messages, ctx.save_skip, turn_latency_ms=ctx.turn_latency_ms)
if not ctx.ephemeral:
    ctx.session.enforce_file_cap(...)                 # 文件条数上限归档（M8）
    self._schedule_background(
        self.consolidator.maybe_consolidate_by_tokens(...))  # 按 token 归并（M6）
self.sessions.save(ctx.session)                          # 原子落盘

真正把新增消息写进 session.messages 的是 _save_turn（loop.py:2039），它还负责截断过大的工具结果、对齐 tool_call_id，保证持久化的历史是「结构合法」的。

5 · 输出：publish_outbound 把回复送回 Bus

RESPOND 组装好 OutboundMessage 后，Loop 通过 self.bus.publish_outbound(...) 送回总线（如 loop.py:1338）。至此 Loop 的职责结束——后续由 ChannelManager 消费 outbound 队列并发到平台（见 M9）。整个回合里 Loop 从不直接碰平台 SDK，只跟 Bus 打交道，这就是「编排层与 I/O 层解耦」。

⚠️ NanoScope 在此处的一处魔改（仅点到，不展开）：resolve_security_context（loop.py:863-885）用 IdentityResolver 把入站消息解析成 SecurityContext，实现多用户身份墙——但这属于 NanoScope 新增能力，已在 NANOSCOPE_LEARNING_GUIDE.html 讲过。multi_user 关闭时它返回 None，行为与 nanobot 基线完全一致，所以不影响你按 nanobot 基础能力理解 Loop。
收口：Loop = 常驻 while 主循环（1s 心跳，loop.py:1118）+ 同会话串行/跨会话并发的 _dispatch（loop.py:1261）+ 7 态回合状态机（TurnState :103 / _TRANSITIONS :241）。它只做「编排」，把「工具循环」下放给 Runner，把「发消息」上抛给 Bus。
M2 Agent Runner（agent/runner.py）—— 通用「工具调用循环」执行器
职责：Runner 是与产品无关的工具循环（docstring："Run a tool-capable LLM loop without product-layer concerns." runner.py:103）。给它一份「初始消息 + 一套工具 + 上限」的 AgentRunSpec，它就反复做「调 LLM → 若模型要调工具则执行 → 把结果回灌 → 再调 LLM」，直到模型给出最终答复或触达上限，返回 AgentRunResult。Loop、Subagent、Cron 都复用它——这就是「shared execution loop」的含义。

1 · 输入契约 AgentRunSpec 与输出 AgentRunResult

Runner 的输入是一个 @dataclass(slots=True) 的 AgentRunSpec（runner.py:60-85），把「跑一次工具循环」需要的一切参数化。几个关键字段：

字段含义
initial_messages起始消息列表（system + 历史 + 本轮 user）——由 Loop 的 BUILD 阶段准备
tools: ToolRegistry本次可用的工具集（M3）——决定模型能调什么
runtime: LLMRuntimeprovider + model + 上下文窗口 + 生成参数的快照

输出是 AgentRunResult（runner.py:89-99）：final_content（最终文本）、messages（完整消息轨迹）、tools_used、usage（token 统计）、stop_reason。AgentRunner.__init__ 只做一件事：持有一个 ContextGovernor（runner.py:106）——这是它和「上下文压缩」模块的连接点。

2 · 核心循环：for iteration in range(max_iterations)

循环主体在 _run_core（runner.py:322），每一轮 第一件事就是「治理上下文」再喂给模型——注意它治理的是发给模型的副本，绝不改动要落库的原始消息（这是「持久化与模型视图分离」的关键设计）：

# runner.py:355-365 —— 每轮先治理上下文副本，再请求模型
for iteration in range(spec.max_iterations):
    # 治理只作用于「发给模型的副本」，不移动 caller 落库用的 append 边界
    messages_for_model = self.context_governor.prepare_for_model(   # ← M6 的入口
        governance_config, messages, compacted_tool_call_ids,
    )
    ...
    response = await self._request_model(spec, messages_for_model, hook, context)

拿到模型响应后分两种情况：模型要调工具（response.should_execute_tools，runner.py:411）就先把 assistant 消息（含 tool_calls）append 进轨迹，执行工具，再把每个工具结果作为一条 role="tool" 消息回灌；模型给出纯文本则收敛为 final_content。工具结果回灌的代码：

# runner.py:454-467 —— 工具结果作为 role=tool 消息回灌到轨迹
for tool_call, result in zip(response.tool_calls, results):
    tool_message = {
        "role": "tool",
        "tool_call_id": tool_call.id,
        "name": tool_call.name,
        "content": self.context_governor.normalize_tool_result(  # 截断/落盘超长结果（M6）
            governance_config, tool_call.id, tool_call.name, result),
    }
    messages.append(tool_message)

3 · 工具执行：串行 or 并发

一轮里模型可能一次要求调多个工具。执行入口是 _execute_tools（runner.py:1090）：当 spec.concurrent_tools=True 时用 asyncio.gather 并发跑，否则顺序跑；单个工具的实际调用在 _run_tool（runner.py:1141），它内部走 ToolRegistry.execute（见 M3）并把异常收敛成「工具错误结果」而不是让整个循环崩掉。

4 · 三道「防失控」阀门

纯工具循环最怕「模型抽风」——空回复、超长截断、无限被注入。Runner 用三个模块级常量兜底（runner.py:54-57）：

常量值防的是什么
_MAX_EMPTY_RETRIES2模型连续返回空内容时的最大重试
_MAX_LENGTH_RECOVERIES3因输出被 length 截断而触发的「续写恢复」最大次数
_MAX_INJECTIONS_PER_TURN3一个回合内允许「回合中注入」用户新消息的最大条数
_MAX_INJECTION_CYCLES5注入-再跑的最大循环数（防注入把回合无限拉长）

「回合中注入」是 nanobot 的一个巧妙能力：回合还在跑时用户又发了消息，Loop 会把它塞进 pending 队列（M1），Runner 在合适的收敛点通过 injection_callback 把这些消息「注入」进当前循环（_drain_injections，runner.py:214-262），并保证角色交替合法（_append_injected_messages，runner.py:125-147）。注入受上面两个常量硬性封顶。

🔁 类比：Runner 像一个「做题—对答案」的自动循环：模型写一步（调工具就是「查资料」），把资料贴回题面，再让模型接着写；直到模型说「我写完了」（纯文本）或者达到「最多写 N 步」。三道阀门就是监考老师：空着交卷最多让你重写 2 次、写超篇最多续 3 次、中途递小纸条最多收 3 张。

4 · 作用域隔离：core vs subagent

这是安全设计的重点。每个工具用 _scopes 声明自己属于哪些作用域（tools/base.py:196，默认 {"core"}）。主 Agent 用 scope="core" 加载完整工具集；子智能体（M10）用 scope="subagent" 加载一套更窄的工具集，并且拿的是独立的 ToolRegistry。这样即使子智能体被恶意 prompt 带偏，它能碰的工具面也天然更小。

🔑 类比：作用域就像门禁卡等级。主 Agent 是「全楼通行卡」，子 Agent 是「只能进资料室的访客卡」——同一套门（工具类），发不同权限的卡（scope），是最省事的最小权限实现。

工具执行时常需要「当前工作区、当前会话、当前请求身份」等运行时信息，这些通过两个载体传入：ToolContext（tools/context.py:75，构造/装配期依赖）与 RequestContext（tools/context.py:20，请求级）。后者用 Python 的 ContextVar 存放（tools/context.py:5、13），使得「当前请求上下文」能在异步调用链里安全传递而不用层层显式传参——这也是 Loop 在跑一个回合前 bind_request_context、跑完 reset_request_context 的原因（loop.py:30 import）。

关键参数 consolidation_ratio 默认 0.5（在 loop.py:273 作为构造参数传入），意思是「一旦超预算，就压到窗口的一半」，留出足够空间给后续对话，避免「压一点点、马上又超、频繁压」。归并出的摘要写进 consolidator_archive.md（模板 templates/agent/consolidator_archive.md）。

4 · ③ AutoCompact：空闲会话的定时压缩

前两层都在「有消息在处理」时触发。但一个会话可能聊到一半就没人理了——它的历史还占着内存/文件。AutoCompact（autocompact.py:18）专治这个：主循环空闲（1s 超时，loop.py:1129）时调 check_expired（autocompact.py:66），扫描所有会话，把「空闲超过 TTL 且有可压缩尾巴」的会话安排后台压缩：

# autocompact.py:74-84 —— 空闲扫描：跳过在跑的会话，压缩过期的
for info in self.sessions.list_sessions():
    key = info.get("key", "")
    if key in active_session_keys:           # 有在跑的任务 → 跳过（避免打架）
        continue
    if self._is_expired(updated_at, now) and self._has_compactable_idle_tail(key):
        self._archiving.add(key)
        schedule_background(self._archive(key, runtime=runtime))

TTL 由 session_ttl_minutes 配（loop.py:272，默认 0 = 关闭）。压缩产物是一段「上次对话摘要」，下次这个会话再被唤起时，COMPACT 状态（M1）通过 prepare_session（autocompact.py:109）把摘要取出注入，用户体验上「接得上」。它实际调的是 Consolidator 的 compact_idle_session（memory.py:1214）。

⚠️ 三条防打架规则：AutoCompact 特意跳过正在处理的会话（autocompact.py:78）、跳过内部会话（如 dream: 前缀，autocompact.py:20/64）、用 _archiving 集合防重复压缩（autocompact.py:83）。这些细节保证「后台压缩」不会和「前台回合」抢同一个 session 造成数据竞态。

build_system_prompt 只产出「一段文本」，把它变成 LLM 要的 messages 数组的是 build_messages（context.py:203）。它做三件事：把上面拼好的 system prompt 放进 {"role":"system"}、后面接上 *history、再把当前用户消息（含图片则转 base64 image block）追加或合并到末尾：

    {"role": "system", "content": self.build_system_prompt(...)},
    *history,                     # M8 提供的历史消息
]

else:

⚠️ 提示词是「每回合重建」的，不是一次性拼好存起来。因为身份里有实时 Runtime、记忆区随用户可见集合变化、Recent History 会增长、session_summary 由后台压缩产生——这些都在变。所以 M1 的 BUILD 状态每回合都会调一次 build_messages（loop.py:1887）。这也解释了为什么 M6 的压缩治理要放在 Runner 每轮做：拼装是「重建全量」，压缩是「削减到能塞进窗口」。
🧩 类比：拼装一份「员工上岗手册」。identity.md 是封面「你是谁、在哪上班」；AGENTS/SOUL/USER 是「公司章程 + 你的性格档案 + 老板偏好」；tool_contract 是「工具使用规程」；记忆区是「客户档案柜（多用户只给你看你负责的那几户）」；技能清单是「你能调用的部门目录」；Recent History 是「最近几天的交接班记录」。ContextBuilder 就是每天上班前把这本手册按固定目录重新装订一遍递给你。

M8 Session / Context（session/）—— 会话持久化、历史裁剪与 key 隔离
职责：Agent 要「记得刚才聊了什么」，靠的就是 Session 层。它有两个核心对象：Session（manager.py:128，一段对话的内存表示：一串 messages + 元数据 + 已归并游标）和 SessionManager（manager.py:413，按 key 管理所有 session 的存取、每个 key 落一个 .jsonl 文件）。再加一个 session key 规则（keys.py）决定「哪些消息算同一个会话」——这就是多用户/多群隔离的第一道边界。

1 · Session：一段对话的内存表示

Session（manager.py:128）是个 dataclass，字段很直白：key（注释写明格式是 channel:chat_id，manager.py:131）、messages（消息列表）、created_at/updated_at、metadata、以及关键的 last_consolidated（已归并到文件的消息数，manager.py:136）。追加消息用 add_message（manager.py:147），它给每条消息盖时间戳后 append：

# manager.py:147-156 —— add_message：盖时间戳后追加
def add_message(self, role: str, content: str, **kwargs) -> None:
    msg = {"role": role, "content": content,
           "timestamp": datetime.now().isoformat(), **kwargs}
    self.messages.append(msg)
    self.updated_at = datetime.now()

last_consolidated 是 M6 Consolidator 的「书签」：它标记「前 N 条已经被归并成摘要了」。所以 get_history（manager.py:158）取历史时是从这个书签往后切的——unconsolidated = self.messages[self.last_consolidated:]（manager.py:171），再按「最多 N 条」和「token 预算」两级裁剪。这就是「压缩过的旧消息不会重复进上下文」的实现点。

2 · SessionManager：按 key 存取 + 原子落盘

SessionManager（manager.py:413）是 session 的仓库。取会话统一走 get_or_create（manager.py:501）：内存有就返回，没有就从磁盘对应的 .jsonl 读回、再没有就新建一个空的。存回磁盘走 save（manager.py:656），它有一个很重要的工程细节——先写临时文件再原子 rename：

# manager.py:667-686 —— 先写 .tmp，再 os.replace 原子替换
tmp_path = path.with_suffix(".jsonl.tmp")
with open(tmp_path, "w", encoding="utf-8") as f:
    f.write(json.dumps(metadata_line, ...) + "\n")   # 首行 = 元数据
    for msg in session.messages:
        f.write(json.dumps(msg, ...) + "\n")           # 每条消息一行 JSONL
os.replace(tmp_path, path)                            # 原子替换：崩溃也不会写坏
⚠️ 为什么要「先 tmp 再 replace」？如果直接往目标文件写，进程在写一半时崩溃，会留下一个损坏的半截文件，下次读回就丢了整个会话。os.replace（manager.py:686）是操作系统级的原子操作——要么看到旧文件、要么看到完整新文件，永远不会看到「写一半」。这是文件式持久化的标准做法。

每个会话文件有容量上限 FILE_MAX_MESSAGES = 2000（manager.py:35），由 enforce_file_cap（manager.py:388）在超限时裁掉最旧的消息（M1 的 SAVE 状态会调它，loop.py:1974）。这保证单个会话文件不会无限膨胀。

3 · session key：隔离的第一道边界

「哪些消息属于同一个会话」由 session_key_for_channel（keys.py:8）决定。默认规则很简单——f"{channel}:{chat_id}"（keys.py:12）：Telegram 的群 A 和群 B、CLI 和 Telegram，key 都不同，历史天然隔离。但有一个「统一会话」开关：

# keys.py:8-12 —— key 规则：默认按 channel:chat_id 隔离，可选统一
def session_key_for_channel(channel, chat_id, *, unified_session=False):

        return UNIFIED_SESSION_KEY        # "unified:default"（keys.py:5）

开 unified_session 时所有渠道共用一个 UNIFIED_SESSION_KEY = "unified:default"（keys.py:5）——适合「个人助理」场景（不管从哪个 App 找它，都是同一段记忆）。关掉则每个聊天窗口独立——适合「群机器人」场景（各群互不串味）。

M9 Bus 与 Channels（bus/ + channels/）—— 消息总线与平台适配
职责：这是 Agent 与外部世界的「I/O 圈层」。Channels（channels/）是平台适配器——把 Telegram/QQ/Discord/CLI 各自五花八门的原始事件，翻译成统一的 InboundMessage；反过来把 OutboundMessage 翻译回各平台的发送 API。Bus（bus/queue.py）是它俩和 Loop 之间的缓冲带——两条异步队列（inbound / outbound）彻底解耦「收发消息」和「处理消息」。核心价值：Loop 永远只跟统一的 Message 打交道，加一个新平台不用改 Loop 一行代码。

1 · Bus：两条异步队列

MessageBus（queue.py:8）本身极简——就是两个 asyncio.Queue：

# queue.py:17-30 —— 两条队列 + 四个存取方法
self.inbound: asyncio.Queue[InboundMessage] = asyncio.Queue()   # :17 平台→Agent
self.outbound: asyncio.Queue[OutboundMessage] = asyncio.Queue()  # :18 Agent→平台

async def publish_inbound(self, msg):  await self.inbound.put(msg)     # :20 Channel 投递
async def consume_inbound(self):       return await self.inbound.get() # :24 Loop 取
async def publish_outbound(self, msg): await self.outbound.put(msg)    # :28 Loop 投递

方向很清晰（docstring queue.py:12-13 也点明）：Channel publish_inbound → Loop consume_inbound（就是 M1 主循环那句 loop.py:1127）；Loop 处理完 publish_outbound（loop.py:1338）→ ChannelManager 消费。队列天然提供「削峰填谷 + 背压」：平台消息来得再快，Loop 也按自己节奏一条条取。

队列里流动的是两个 dataclass：InboundMessage（events.py:23，含 channel/chat_id/sender_id/content/media 等）和 OutboundMessage（events.py:47，含目标 channel/chat_id/content）。此外还有个 RuntimeEventBus（runtime_events.py:91）走「流式增量/进度事件」的旁路，不与主消息队列混流。

2 · Channels：平台适配的抽象基类

所有平台适配器都继承 BaseChannel（base.py:21，ABC）。它规定了两个方向的契约：入站用 _handle_message（base.py:218）——平台 SDK 收到消息后调它，它做完鉴权就把消息 publish_inbound 进总线（base.py:279）；出站用抽象方法 send（base.py:92）和流式 send_delta（base.py:104）——每个具体平台自己实现「怎么调它的 API 发消息」。

_handle_message 里有个设计细节值得看：它把「发送者身份」和「授权主体」分开（base.py:236，permission_id = authorization_id if ... else sender_id）——群聊里可以按「群」授权而不改「发言人」身份。鉴权不通过且是私聊时，还会自动回一个配对码（base.py:238-247），这就是 /pairing 命令的另一半。

3 · ChannelManager：启动所有渠道 + 出站分发

ChannelManager（manager.py:81）管所有渠道实例。start_all（manager.py:465）在启动时把每个 channel 拉起（各自监听自己的平台）；同时它跑一个 _dispatch_outbound（manager.py:571）常驻协程，不停从 bus.consume_outbound 取消息（manager.py:586），按 msg.channel 找到对应 channel 调它的 send 发出去。这里还做了流式增量的「合并（coalescing）」优化（manager.py:575-577 的 pending 缓冲）。

⚠️ 为什么要 Bus 这层间接？如果 Loop 直接调各平台 SDK，就会被绑死在具体平台上，且收发速率必须严格匹配。加一层队列后：① Loop 只认统一 Message，平台适配全在 Channel 里；② 收发解耦，任一侧慢了另一侧不阻塞；③ 天然支持「一条消息进、多条渠道出」（跨渠道投递）。这是「适配器模式 + 生产者消费者」的经典组合。
📮 类比：跨国邮局。Channels 是各国的「收件/投递窗口」（懂当地语言和邮编格式，把信统一翻译成国际标准信封 = InboundMessage）；Bus 是邮局内部的「待处理筐 / 待寄出筐」两个筐；Loop 是分拣中心（只看标准信封，不管这信原来是中文还是日文）。加一个新国家的业务，只需开一个新窗口，分拣中心完全不用改。
收口：I/O 圈 = Bus（MessageBus queue.py:8：inbound:17/outbound:18 两队列 + publish/consume :20/:24/:28）承载 InboundMessage/OutboundMessage（events.py:23/47）+ Channels（BaseChannel base.py:21：入站 _handle_message:218→publish_inbound:279 / 出站 send:92；ChannelManager manager.py:81：start_all:465 / _dispatch_outbound:571）。适配器 + 队列，让 Loop 与平台彻底解耦。
M10 Skills / Subagent / Command —— 技能加载、子智能体与斜杠命令
职责：这三个模块是 Agent 的「可扩展性三件套」。Skills（agent/skills.py）让能力以「文件夹 + SKILL.md」的形式插拔式扩展，不改代码就能加技能；Subagent（agent/subagent.py）让主 Agent 能派生一个「窄权限、独立上下文」的子智能体去干专项活；Command（command/）是斜杠命令路由，把 /new /stop /model 这类控制指令与普通对话分开处理。它们分别对应「加能力、加并发、加控制」。

1 · Skills：文件式技能包

SkillsLoader（skills.py:21）扫描两处目录：workspace 下的 skills/ 和内置 builtin 技能，每个技能就是一个含 SKILL.md 的文件夹。list_skills（skills.py:51）列出所有可用技能（workspace 同名覆盖 builtin，skills.py:61-66；还会按 _check_requirements 过滤依赖不满足的，skills.py:71-72）。关键设计是「按需加载」：system prompt 里只放技能的清单摘要（build_skills_summary，skills.py:111），完整的 SKILL.md 要等模型决定用了才 read_file 读进来——这正是 skills_section.md 模板里那句「To use a skill, read its SKILL.md file」的由来（见 M7）。

⚠️ 为什么不把所有 SKILL.md 全塞进 prompt？技能可能几十个，全量注入会瞬间撑爆上下文、也浪费 token。所以只注入「一句话摘要 + 名字」当目录，模型想用哪个再按名 read_file 拉全文。这是「渐进式披露（progressive disclosure）」——把上下文预算花在刀刃上。

2 · Subagent：窄权限的子智能体

SubagentManager（subagent.py:82）负责派生子智能体。spawn（subagent.py:219）接一个 task 描述，起一个独立的 Runner 循环去完成，最后用 _announce_result（subagent.py:386）把结果回报给主 Agent。它的精髓在 _build_tools（subagent.py:197）——给子 Agent 装配一套独立且更窄的工具集：

# subagent.py:204-216 —— 子 Agent 用独立 registry + subagent 作用域
registry = ToolRegistry()                              # 全新的注册表，与主 Agent 隔离
ctx = ToolContext(config=cfg, workspace=..., ...)
ToolLoader().load(ctx, registry, scope="subagent")     # :216 只装 subagent 作用域工具

回顾 M3：工具类用 _scopes 声明自己属于哪些作用域（默认 {"core"}）。这里 scope="subagent"（subagent.py:216）只会装配声明了 subagent 作用域的工具——子 Agent 天然拿不到危险的全量工具（例如不能再 spawn、不能改配置）。加上独立的 ToolRegistry 和独立上下文，子 Agent 就是一个「沙盒里的小号」，跑完即弃、不污染主会话。

3 · Command：三级斜杠命令路由

CommandRouter（router.py:53）把控制类指令与普通对话分流。它的 docstring 讲得很清楚——三级路由，按序匹配（router.py:56-61）：

层级时机典型命令入口
① priority在 dispatch 锁之前处理（要能打断正在跑的回合）/stop /restart /statusdispatch_priority（router.py:95）
② exact在 dispatch 锁内精确匹配/new /model /history /goal /dream /skill /helpdispatch（router.py:103）
③ prefix最长前缀优先（带参命令）如 "/team "dispatch（router.py:111）

为什么 /stop 要放「priority、锁外」？因为它的使命就是打断正在处理的回合——如果它也排队等锁，那就永远得等当前回合跑完才能停，失去意义。所有内置命令在 register_builtin_commands（builtin.py:986）里登记：router.priority("/stop", ...)（builtin.py:988）、router.exact("/new", ...)（builtin.py:991）等，共约 12 条（/new /stop /restart /status /model /history /goal /trigger /dream /skill /help /pairing）。M1 回合状态机的 COMMAND 状态（loop.py:1821）就是调这个路由——命中命令就直接返回，不进 LLM 循环。

🧰 类比：一家装修公司。Skills 是「工具间的技能手册目录」（想学贴瓷砖再去翻那本，不用把所有手册背在身上）；Subagent 是「临时招的专项分包工」（只给他进这一个房间的钥匙，干完结账走人）；Command 是「对讲机上的快捷指令」（喊「停工」要能立刻打断，不能排在正常派活后面）。三者让这家公司既能接新活、又能并行干、还能随时管控。
收口：可扩展三件套 = Skills（SkillsLoader skills.py:21：list_skills:51 / build_skills_summary:111，渐进式披露，只注入摘要）+ Subagent（SubagentManager subagent.py:82：spawn:219 / _build_tools:197 用 scope="subagent":216 装窄工具集 + 独立 registry）+ Command（CommandRouter router.py:53：priority/exact/prefix 三级，dispatch_priority:95 / dispatch:103，register_builtin_commands builtin.py:986 约 12 条命令）。分别对应加能力/加并发/加控制。

⚠️ 一个反复出现的设计母题：「持久化视图」与「模型视图」分离。贯穿全链路你会看到同一个原则——落库的历史（M8 Session、M5 history.jsonl）是事实真相，只增不改；而发给模型的消息（M6 Governor 每轮治理的副本、M7 每回合重建的 prompt）是临时视图，可裁剪、可压缩、可重排。Runner 每轮 prepare_for_model（runner.py:361）治理的绝不是落库边界。理解这条线，就理解了为什么这个 Agent 能「长期记得、又不被上下文压垮」。
🎬 类比：一部电影的拍摄与放映。用户消息是「一场戏的开拍」；Channels/Bus 是「场记板 + 传送到剪辑室」；Loop 是「导演」（喊 action、分镜、决定这条过不过、存不存档）；Runner 是「演员反复对戏直到 NG 消失」；Providers 是「外请的大牌主演（LLM）」；Tools 是「各种道具」；Memory/Session 是「胶片仓库」；压缩四层是「剪辑师」（把长素材剪成能放映的成片，但原始胶片永远留底）。三条后台节律是「夜里默默整理片库、写拍摄日志的场务」。全片看下来，你就懂了这套「Agent 制片厂」怎么运转。
全书收口：一个 nanobot 式 Agent = I/O 圈（Channels+Bus，M9）把世界标准化 → 编排层（Loop，M1）管回合生命周期（7 态 + 同会话串行）→ 执行层（Runner，M2）跑「LLM↔工具」收敛循环 → 能力层（Providers/Tools/Memory/Session/Prompt/压缩/扩展，M3–M8·M10）各司其职。加一条后台节律（空闲压缩、Dream、出站分发）支撑长程运行。抓住「持久化视图 vs 模型视图分离」这条主线，整套框架就从一堆文件变成了一台你能讲清楚的机器。
