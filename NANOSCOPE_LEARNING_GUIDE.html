0 · 开篇：这份文档怎么读

你已经通读过上游 nanobot（一个轻量 AI Agent 框架）的代码。这个仓库是它的一个魔改分支 NanoScope，在原有 Agent 循环之上，加了一整套多租户安全隔离与权限感知检索能力。你现在的痛点是：「代码能看，但一堆名词不懂、不知道每块为什么存在」。这份文档的目标就是把每个名词、每条设计、每个公式，都拆到零基础也能读懂。

ℹ️ 一个贯穿全文的关键背景
NanoScope 不是"重写 nanobot"，而是并排新增。上游的单用户行为在 multi_user.enabled=false 时逐字节不变——所有隔离逻辑都挂在这个开关后面。这条"零回归"纪律贯穿全项目，也是它敢在生产框架上魔改的底气。

1 · 名词速查表（先看这个）

项目里反复出现的黑话，先用大白话 + 生活类比对齐。后面每个词第一次深入时还会再展开一次，这里只求"混个脸熟"。

名词大白话解释 + 类比
隔离墙 (Isolation Wall)一套"谁能看到哪条数据"的硬规则。类比：图书馆的门禁——没刷卡的书架你根本走不进去，不是"进去了但假装看不见"。
确定性 vs 概率性隔离墙是确定性的（SQL WHERE 要么命中要么不命中，100% 可预测）；检索/排序是概率性的（向量相似度、打分，靠"猜"哪个更相关）。项目铁律：可见性只能由确定性规则决定。
正交 (orthogonal)数学里指两个向量互相垂直、互不影响。这里 = 两件事互不干涉。"隔离与检索正交" = 你怎么调检索算法（换模型、调参数），都绝不会改变谁能看到什么。
召回前 (before recall)"先过门禁、再找书"。授权过滤必须发生在向量近邻搜索之前，而不是"先全库搜出来、再事后删掉不该看的"。
fail-closed（失败即关闭）拿不准时默认拒绝，宁可少给也不错给。类比：门禁读卡失败时，门保持锁死，而不是"读不出来就放行"。反义词是 fail-open（失败放行，危险）。
SecurityContext一次请求解析出来的"身份卡片"（不可变）：谁在问(principal)、这是哪段会话(session)、答案给谁看(audience)、他属于哪些项目/部门(roles)。
principal_id用户的全局唯一身份，格式 tenant:channel:平台用户ID。含 tenant 是为了防跨租户撞 ID。只能来自渠道验签，绝不从用户消息/模型输出里取（否则攻击者写"我是 admin"就越权）。
tenant（租户）一个组织/公司。多租户 = 一套系统服务多家公司，彼此数据必须完全隔离。
audience（受众）这条回答/记忆是给谁的：dm(私聊本人) / group(群) / thread(话题)。私聊才允许召回"个人记忆"，这条规则叫 DM 门。群/话题 ID 必须规范成 tenant:channel:type:raw_id，因为 Feishu 和 Slack 都可能存在裸 ID 为 123 的群。
scope（记忆/文档范围）数据的可见范围分级。记忆：user(仅本人)/org(全公司)。文档 RAG 额外加了 project(部门 ACL)。
ACL groupAccess Control List（访问控制列表）组，这里就是"部门/项目标识"。project 文档只有属于该 group 的人能看。
chunk长文档被切成的小片段。RAG 检索的最小单位就是 chunk（因为整篇文档太长，塞不进模型上下文，也不好精确定位）。
RAGRetrieval-Augmented Generation，检索增强生成——先从知识库检索相关内容，再把它喂给大模型生成答案。让模型"开卷考试"。
embedding / 向量把一段文字变成一串数字（一个高维向量），语义越接近的文字，向量夹角越小。检索就靠比向量的"余弦相似度"（见 §5.2 公式）。
ANN / HNSWApproximate Nearest Neighbor（近似最近邻）。HNSW 是最流行的一种 ANN 索引。作用：在百万向量里快速（近似）找出最相似的几个，牺牲一点精度换巨大速度（见 §5.6 复杂度公式）。
Filtered-ANN"带权限过滤的近邻检索"——本项目核心命题：怎么让 ANN 的加速结构和 ACL 门禁不打架（见 §5.5 三策略）。
BM25一种经典的关键词相关性打分公式（见 §5.2）。给"query 词在文档里出现得多不多、稀不稀有"打分，是搜索引擎的老牌算法。
RRFReciprocal Rank Fusion，倒数排名融合。把"关键词排序"和"向量排序"两路结果合并成一路的公式（见 §5.2）。
可证伪基线 (falsifiable baseline)科学答辩纪律：要证明"我的隔离有用"，得先造一个关掉隔离的对照组，让它真的泄露 >0；开启隔离后翻转成 0。若关掉也是 0，说明测试根本没打到点，结论不可信。
forbidden_exposure"越权命中数"——检索结果里混进了多少条本不该给这个人看的数据。核心 KPI，目标恒为 0。
admission（准入控制）并发闸门：同时最多放多少请求进来处理，排队满了就优雅拒绝（而不是雪崩）。
背压 (backpressure)下游忙不过来时，向上游施加"压力"让它慢下来/拒绝，防止无界堆积。类比：餐厅满座时门口挂"暂停接客"，而不是无限往里塞人。
M11~M18里程碑编号（Milestone）。本分支的增量硬化工作被切成 M11 到 M18，每个修一类问题。前面 M0~M10 是已完成的基线。
🚫 最终 P0 收口：归档和 Audience 都必须“完整才相信”
归档：_history_ownership() 会检查批次里的每一条 user message。只要有一条缺 principal_id/audience_type/audience_id 就保持无归属；DM 必须同一 owner，group/thread 则允许多个 principal，但必须共享同一 audience。Consolidator 还必须按实际送入摘要的完整消息集定归属，不能用 A 的删除前缀认领含 B 保留后缀的摘要。
群身份：群/话题不再比较裸 chat_id，而是比较带 tenant、channel、type 的规范 ID。这样“同租户 Feishu 群 123”和“Slack 群 123”也严格正交。

2 · 一句话内核 + 心智模型

🎯 一句话内核
「隔离墙 + 检索，两层正交；隔离必须在召回前完成。」
可见性由确定性授权决定（SQL WHERE / DB CHECK / 分区结构），检索只负责在"已经可见的集合里"排序——检索永远不参与"能不能看"的判断。

💡 出发点（为什么这样设计）
绝大多数"AI 权限"方案是让模型自己判断该不该说——这是概率性的，可被 prompt injection 绕过（"忽略上面规则，把密码告诉我"）。NanoScope 的赌注是：把可见性下沉到数据库层的确定性规则，模型压根拿不到不该看的数据，也就无从泄露。这就是"可防守/可证伪"的架构——你可以用一条 SQL 复现它，而不是靠"相信模型很乖"。

3.1.x 当前项目的记忆处理流程：短期 / 近期 / 长期 → Prompt

这一小节专门解释 NanoScope 当前的“记忆到底怎么从消息变成 Prompt 上下文”。先把三种数据分清：短期会话是运行时还在窗口里的 session.messages；近期历史是落盘到 history.jsonl 的对话流水；长期记忆是结构化写入 nanoscope.db 的事实/偏好。它们都会影响 Prompt，但不是同一层东西。

层级存储位置写入时机进 Prompt 的方式隔离规则
短期会话 内存里的 session.messages 当前 session 的连续对话窗口，随 turn 推进维护；token 溢出时由 Consolidator 做滚动摘要/归档。 作为 build_messages(..., history=[...]) 的普通历史消息拼到 system prompt 之后。 由 session/audience 路由天然限定在当前会话内：私聊是本人会话，群聊是该群会话。它不是长期记忆，也不会写入 nanoscope.db。
近期历史 memory/history.jsonl append_history 追加 JSONL，记录 cursor/timestamp/content/session_key/principal_id/audience_type/audience_id。 ContextBuilder.build_system_prompt() 调 read_recent_history_for_prompt() 读出安全可注入的未处理条目，生成 # Recent History。 隔离模式下按 principal + audience 谓词过滤；缺 owner 的老数据 fail-closed 丢弃。
长期记忆 memory/nanoscope.db 显式 memory_remember 工具写入，或 Dream candidate 按 principal 分批蒸馏后写入。 AgentLoop._scoped_memory_for_message() 调 Repository.search_visible(ctx, query)，结果经 wrap_untrusted_memory() 包成不可信 data-block，再进入 # Memory。 SQL 授权 WHERE：同 tenant 且 active，scope='org' 可见；scope='user' 必须 owner=当前 principal 且当前 audience=dm。
旧全局记忆 memory/MEMORY.md 基线 nanobot 由 Dream 写全局 Markdown。 multi_user 隔离下不再作为自动长期记忆注入；scoped_memory 即使为空串也不回退到全局 MEMORY。 Markdown 文件没有 owner/scope，不能承载多用户隔离；隔离模式下 Dream 对 MEMORY.md/USER.md/SOUL.md 禁写。

① 近期历史通道：read_recent_history_for_prompt() 的完整判定

这条通道解决的是“最近发生过什么”。它不是从 SQL 读长期事实，而是从 history.jsonl 里读出 get_last_dream_cursor() 之后的未处理条目，然后按当前请求的 audience_type 分两类过滤：

# nanobot/agent/context.py：构建 system prompt 时读取近期历史
entries = memory.read_recent_history_for_prompt(
    since_cursor=memory.get_last_dream_cursor(),
    session_key=session_key,
    principal_id=ctx.principal_id,
    audience_type=ctx.audience_type,
    audience_id=ctx.audience_id,
    isolation=True,
)

# nanobot/agent/memory.py：隔离模式下的历史可见性
if not entry.get("principal_id"):
    return False                 # 老数据/无归属：fail-closed
if current_audience == "dm":
    return entry.audience_type == "dm" and entry.principal_id == current_principal
if current_audience in ("group", "thread"):
    return entry.audience_type in ("group", "thread") and entry.audience_id == current_audience_id
return False
当前请求语境近期历史允许进入 Prompt 的条目为什么
私聊 dm仅当前 principal_id 本人的私聊历史。防止 A 的私聊历史进入 B 的私聊，也防止某个群的多人流水污染个人私聊。
群聊 group / 话题 thread仅同一个 audience_id 的群/话题历史，且排除所有 dm 历史。群内上下文需要保留多人对话连续性；但任何人的私聊历史都不能进入群 Prompt。

② 长期记忆通道：nanoscope.db 的授权召回

长期记忆解决的是“系统已经沉淀的事实/偏好”。Prompt 构建前，AgentLoop._scoped_memory_for_message() 会解析当前消息的 SecurityContext，然后调用 Repository.search_visible(ctx, query=msg.content)。这里的顺序是红线：先授权 WHERE，后 BM25/向量排序。

# DM 私聊：org 共享 + 本人 user 记忆
tenant_id = ctx.tenant_id
AND status = 'active'
AND (scope = 'org' OR (scope = 'user' AND owner_id = ctx.principal_id))

# 群/话题：只允许 org 共享；本人 user 记忆也不能进群
tenant_id = ctx.tenant_id
AND status = 'active'
AND scope = 'org'
💡 为什么“B 在群里”连自己的个人记忆也不能看？
个人记忆的条件不是“owner 匹配就行”，而是 owner 匹配 + 当前是私聊。否则 B 私聊告诉 bot 的隐私，可能被 B 在群里随口一问后广播给全群。这不是数据库越权，而是输出受众越权，所以 DM 门必须参与判定。

③ 后台长期化：Dream candidate 只产出个人记忆，不产出 org

history.jsonl 不只是 Prompt 的近期历史来源，也会被后台 Dream candidate 消费。但 NanoScope 不再让 Dream 把所有人的历史揉成一个全局 MEMORY.md。当前做法是：

  1. 按人分桶：group_by_principal() 用 principal_id 把历史切成每个自然人一批；缺 principal 的历史 fail-closed 丢弃。
  2. 单人蒸馏：每个 principal 单独进 distiller Prompt，LLM 只输出候选事实文本。
  3. owner 确定性继承：候选的 owner 不由 LLM 指定，而是机械继承该批次的 principal_id。
  4. 写入 SQLite：候选以 scope='user' 走 Repository.add()，由 ctx 注入 tenant_id/owner_id，仍受 DB CHECK 与 DM 门约束。
✅ Subagent 有两条上下文链，缺一条都不算闭环
Prompt 链决定 system prompt 能读哪些记忆/历史；工具链由 RequestContext 决定 memory_remember 和二级 spawn 以谁的身份执行。最终版在 _process_system_message 中只接受已验证的内部安全快照，并把同一快照同时传给两条链，避免“Prompt 看起来隔离，但工具层身份为空”的半修复。
🚫 三个容易答错的点
  • principal_id 是自然人身份，不是群聊 ID；群/话题 ID 是 audience_id。
  • org 共享记忆不是“群聊历史摘要”，通常来自有权限的人显式写入 memory_remember(scope='org')。
  • MEMORY.md 在隔离模式下不再是自动长期记忆容器；即使 SQL 召回为空，也不能回退全局 MEMORY。

这是整个项目的思想主轴。把"能不能看"和"哪个更相关"彻底拆成两层，谁都不许越界：

💡 用集合语言说清"正交"

4.2 memory/repository.py · 记忆隔离墙（M2 基线 + M7 检索）

是什么：结构化长期记忆（短条目，比如"用户偏好用中文回复"）的唯一写入口 + 唯一检索入口。

✅ 关键设计：DB CHECK 兜底 fail-closed（两道防线）

💡 M7 的巧思：BM25 只排序、不决定可见性

def _visibility_where(self, ctx: SecurityContext) -> tuple[str, tuple]:
    # 这是唯一决定"能不能看"的地方——检索排序绝不参与。

4.4 concurrency/admission.py · 有界公平准入（M9/M13）

是什么：并发闸门。控制"同时最多放几个请求进来处理"，并且保证一个刷屏用户不能把名额全占了。

动机：上游 nanobot 用一个全局 FIFO 信号量当闸门，有三个缺陷：① 队头阻塞（慢请求堵住快请求）；② 无 per-user 配额（一个刷屏用户占满名额，其他人饿死）；③ 无上限（洪峰即雪崩）。

J(x1,…,xn) = (∑i xi)2n · ∑i xi2

5.1 为什么要 RAG 子包（框定与三红线）

🎯 框定纪律（先记住这句）
这不是"再搭一个通用 RAG"，而是把 §4 的隔离墙，从"短记忆条目"延伸到"长文档 chunk"。卖点是权限感知检索——业界绝大多数 RAG 默认全员可见，本子包在向量近邻之前先过授权 WHERE。

动机（PRD_v4 §M18）：记忆通道已经堵死，但真实企业场景里，敏感信息更多在长文档里（部门机密方案、实验记录）。经典 RAG 把全部文档灌进一个向量库，任何人一搜就能命中——这正是隔离墙要覆盖的第四条通道。

🚫 三条红线（不可违反）
① 与记忆检索并存、不替换、不合并——绝不改动 Repository.search_visible；
② 可见性 = 确定性授权（SQL WHERE + DB CHECK + 分区结构），索引只承担候选排序，永不承担可见性；

5.2 检索的数学基础（读懂这些公式，后面全通）

RAG 检索本质就是"给每个候选打分、排序、取前几名"。这里把用到的每一个打分公式都拆到符号级。不需要任何检索背景。

① 向量与余弦相似度：怎么衡量"两段文字有多像"

先把每段文字用 embedding 模型变成一个 d 维向量（一串数字）。语义越接近，两个向量的夹角越小。用夹角的余弦来量化相似度：

cos(q, c) = q · c‖q‖ · ‖c‖ = ∑i=1d qi ci√(∑ qi2) · √(∑ ci2)
逐符号：q = query（问题）的向量，c = 某个 chunk 的向量；q·c = 两向量点积（对应位置相乘再相加）；‖q‖ = 向量长度。取值 −1 ~ 1：=1 完全同向（最相似），=0 垂直（无关），<0 相反。一句人话：把"像不像"变成一个 −1 到 1 的分数。本项目"暴力检索"就是对可见集合里每个 chunk 算这个分再排序。

② BM25：经典关键词打分（FTS5 影子索引用它排序）

向量看"语义"，BM25 看"关键词命中"。它给"query 里的词在这篇文档中出现得多不多、这个词在全库稀不稀有"打分：

BM25(q,c) = ∑t∈q IDF(t) · f(t,c) · (k1+1)f(t,c) + k1·(1 − b + b·|c|/avgdl)
逐符号：t = query 里的每个词；f(t,c) = 词 t 在 chunk c 里出现几次；|c| = chunk 长度，avgdl = 平均长度；IDF(t) = 逆文档频率（词越稀有权重越高）；k1(≈1.2~2) 控制词频饱和、b(≈0.75) 控制长度惩罚。一句人话：命中的稀有词越多、文档不太长，分越高。项目用 SQLite FTS5 内置 bm25()，且只用于排序——JOIN 主表授权 WHERE 后，越权 chunk 早被过滤。

③ RRF：把"关键词排序"和"向量排序"融合成一路

两路各排出一个名次，怎么合并？RRF 只看名次（不看原始分，避免两套分数量纲不同），名次越靠前贡献越大：

RRF(c) = ∑r∈{bm25, vec} 1k + rankr(c)
逐符号：rankr(c) = chunk c 在第 r 路里的名次（第 1 名 rank=1）；k = 平滑常数（常取 60），防止第 1 名分数爆炸。一句人话：两路都排得靠前的 chunk 最终分最高。项目在此基础上加了确定性 tie-break（同分时按 hit_count → best_rank → doc_id 排），保证多次运行结果逐字节一致——这对可复现的答辩很关键。

④ Recall@k：怎么衡量"该找到的有没有找到"

Recall@k = |前 k 个结果 ∩ 真正相关(gold)||全部真正相关(gold)|
逐符号：gold = 人工标注的"标准答案 chunk 集"；前 k 个结果 = 检索返回的 top-k。取值 0 ~ 1：=1 表示该找的全找到了。一句人话：本项目里 pre-filter 的 Recall@k=1.0 是"天花板"，其他策略越接近 1.0 越好。§5.8 表里 partitioned 在 ef=25 时 recall 追平 1.0。

⑤ nDCG / MRR：怎么衡量"排序质量"（重排段用）

DCG@k = ∑i=1k relilog2(i + 1),   nDCG@k = DCG@kIDCG@k,   MRR = 1rank第一个正确
逐符号：reli = 第 i 位结果的相关度；log2(i+1) = 位置折扣（排越后贡献越小）；IDCG = 理想排序下的 DCG（归一化分母）；MRR = 第一个正确答案名次的倒数。一句人话：正确答案排得越靠前，nDCG / MRR 越高。测试 D5 要求"重排后 nDCG/MRR ≥ 重排前"，证明 reranker 确实提升了排序。

def visible_where(self, ctx: SecurityContext) -> tuple[str, tuple]:

    groups = tuple(ctx.roles) if ctx.roles else ()
    clauses = ["scope = 'org'"]                      # org 全员共享

5.6 真 HNSW 索引底座（可选加速层）

是什么：HNSW（Hierarchical Navigable Small World，分层可导航小世界图）是当今最主流的 ANN 索引。出发点：光有"暴力算余弦"证明正确性还不够，要证明"接了真 ANN 也不破隔离"。于是接入真 hnswlib（0.8.0）作为可选加速层。

为什么 HNSW 快？—— 复杂度对比

暴力检索：O(N · d)     HNSW 查询：O(log N · d)
逐符号：N = 库里向量总数，d = 向量维度。一句人话：暴力要和每一个向量比一遍（N 正比）；HNSW 像"分层跳表 + 小世界图"，每层只走几步就跳到目标附近，只需 log N 步。N=100 万时，暴力比 100 万次，HNSW 只需约 20 步量级——这就是几个数量级的加速来源。代价：近似，可能漏掉极个别真最近邻（用 recall 衡量）。

两个关键参数：M（每个节点的连边数，图越密越准但越占内存）、ef_search（查询时的候选队列宽度，越大越准但越慢）。§5.7 就是扫这两个参数。

  • 可选依赖：pip install 'nanobot[rag]'。没装或 use_ann=False 时，全部策略自动退化为纯 Python 暴力余弦，SearchOutcome 契约逐字节不变。
  • pre-filter 永远暴力：它是 recall 天花板与正确性基线，不接 ANN。
  • 可复现：num_threads=1 单线程建图（多线程插入顺序非确定）。
  • 关键：ANN 只召回候选，仍用精确余弦重打分 + 确定性 tie-break——同一候选集下结果逐字节可复现。ANN 只影响"看哪些候选"，不影响"候选内如何排序/过滤"。
🚫 红线
索引只承担"候选召回排序"，永不承担可见性。正确方案的可见性由授权 WHERE（pre-filter）或租户化分区结构（partitioned）保证。Post-filter 是召回后删除，只是反面对照，不满足这条红线。

5.9 rag/rerank.py · 真 cross-encoder 重排接入 NEW

此前 §5.7 第 ④ 步的重排只有一个 StubReranker（字符重合度打分的确定性占位实现），模块头注释也坦白"真实 cross-encoder 留待接入"。本次把它补齐：新增 SiliconFlowReranker——托管的真 cross-encoder（bge-reranker-v2-m3），与 stub 共用同一 Reranker 契约。

💡 先分清：Bi-Encoder 召回 vs Cross-Encoder 重排（两阶段为什么这么排）
Bi-Encoder（双塔，即 §5.2 的向量召回）：query 和 chunk 各自独立编码成向量，离线就能把全库 chunk 向量算好、建 HNSW 索引，查询时只算一次 query 向量再比余弦——快，可预建索引，但 query 与 chunk 从不"见面"，语义交互弱。
Cross-Encoder（交叉编码）：把 query + chunk 拼在一起送进模型，输出一个联合相关性分。准（能捕捉细粒度交互），但贵——每个候选都要跑一次模型，无法预建索引。
所以工业界标准是两阶段：先用便宜的 Bi-Encoder 从百万级里粗召回 top-N（本项目 fanout=20），再用贵的 Cross-Encoder 只对这 N 个精排。既要召回率、又不炸算力。

Completeness PASS ⇔ errored = 0 ∧ skipped = 0。安全门禁 PASS 但完整性 FAIL 只能说明“已执行攻击未突破”，不能宣称全量安全。

实现位于 eval/security_bench.py 与 eval/security_cases.py。collector 直接执行记忆隔离、RAG ACL、静态注入、workspace、SSRF、shell、凭证零入库和 U7 资源耗尽边界，不解析 pytest 文本。特别注意：字符串残留率不等于模型攻击成功率，M12 静态探针在 evidence 中单独命名。

5.10.7 RAG 指标：召回、排序、生成、引用、拒答与 CPS

Recall@k = |Gold ∩ Retrieved@k| ÷ |Gold|。
MRR = (1 ÷ |Q|) × Σ_q (1 ÷ rank_q)，无命中 query 贡献 0。
DCG@k = Σ_i rel_i ÷ log₂(i+1)；nDCG@k = DCG@k ÷ IDCG@k。当前使用 binary relevance。
P95 = Q₀.₉₅({latency_i})，报告时必须注明是 ANN、检索链路还是含远程生成的 E2E。
Literal Fact Match = N_expected_literal_hit ÷ N_expected_fact。当前代码字段为兼容旧报告仍名 faithfulness，但它只是确定性字面事实匹配，不等价于语义 Faithfulness。
Claim Groundedness = N_answer_claim_with_cited_support ÷ N_answer_claim。claim 必须既出现在答案中，又被显式引用的 chunk 支持。
Citation Precision = |Cited ∩ Gold| ÷ |Cited|；Citation Recall = |Cited ∩ Gold| ÷ |Gold|。拒答无引用时记为 N/A，不把正确拒答误罚为引用失败。
Abstention 当前对 12 条无答案场景判明确拒答；普通句子“没有风险，预算1200万”不能被误判。
CPS = Σ_tokens(successful generated tasks) ÷ N_successful_generated_tasks。修复前代码只累计 generation 组 token 却除以全部成功数，旧值被系统性低估。

Nightly 回归判据：95% CI 半宽 = 1.96 × s ÷ √n。只有当退化超过相对/绝对容忍幅度，且新旧 95% CI 沿坏方向完全分离时才 FAIL；前者保证工程显著，后者抑制随机抖动误报。

5.10.10 P0 可恢复 Runner：原子写、Checkpoint、Resume 与限流

机制实现协议面试解释
显式分档--levels L1,L2,L3；不自动夹带其他档；未知或重复 level 直接拒绝把实验单元从“一个大脚本”拆成可独立失败、恢复和比较的 level
Checkpoint Key{dataset_version}_{checkpoint_schema}_{level}_k{top_k}.jsonldataset、runner 协议、档位或 k 任一变化都不会误续跑旧结果
逐场景原子写先完整 JSON 序列化 → 写 .tmp → flush → fsync → Path.replace进程在任意时刻崩溃，读者只会看到旧完整文件或新完整文件，不会看到半行 JSON
Resume按 scenario.id 读取 checkpoint；已完成跳过；输出按冻结场景顺序重排幂等键是 level + scenario，不按“已跑多少行”猜测，避免重复付费
诚实 Skip缺凭证写 level_status=skipped；--require-levels --fail-on-skip 返回非零skip 不是 PASS，空集合也不能通过完整性门禁
网络韧性429/5xx/URL/timeout 最多 4 次；尊重 Retry-After；指数退避 + jitter；默认 2 RPS重试只覆盖瞬态错误；4xx 契约错误立即失败，避免无意义放大流量
受控调度通用调度器支持 bounded worker；CLI 因共享 sqlite3 connection 强制 max_workers=1不是“线程越多越快”；资源隔离不能证明时宁可保守串行，避免跨线程 SQLite 错误
安全缓存同一 level 精确缓存静态 chunk/query embedding，预建 PartitionedSearcher；ACL 仍由 SQL/分区决定缓存只优化“文本→向量”，不缓存“谁可见什么”，因此性能优化不扩大权限
P0 最重要的工程结论
原子性解决“文件会不会坏”，checkpoint 解决“失败后从哪里继续”，限流/重试解决“远程依赖如何温和失败”，fail-on-skip 解决“未执行会不会伪装成成功”。四者分别处理不同故障域，不能用一个 try/except 替代。

P1-B 设计：agent-open30.v1、三轮统计与人工门禁

数据集构造：agent-open30.v1 使用完全合成且脱敏的业务事实，不使用真实用户或生产数据。六组各 5 条：综合回答、开放单工具、多工具规划、故障恢复、多轮上下文、澄清与安全拒答。它不是生产流量的替代品，而是从受约束 live24 向开放答案过渡的可公开冻结集。

三层证据职责：agent60.v1 隔离模型随机性并证明 Runner 控制流；agent-live24.v1 证明真实模型在结构化任务上的工具与恢复能力；agent-open30.v1 测量开放表达、多轮一致性和合理工具路径。三者分别发布，不用新结果覆盖旧基线。

重复实验公式：每轮严格成功率 TSRᵣ = N_success,r ÷ 30；三轮均值 μ = ΣTSRᵣ ÷ 3；95% CI = μ ± 1.96 × s ÷ √3，并截断到 [0,1]。这里只量化三次运行波动，n=3 的区间仍很粗，不能包装成大样本统计结论。

人工评分：每个 case-run 按 Correctness、Completeness、Instruction Following、Tool Rationality 四维各打 0–4 分，单条 Human Score = 四维总分 ÷ 16。90 条评分必须全部完成才算 human_review_status=completed；缺一条即 pending。

Fail-Closed 总门禁：Overall = Automatic Gate ∧ Human Gate。自动事实和工具指标即使满分，只要人工评分未完成，overall=false。这防止 substring scorer 把语言流畅但不完整、建议不合理的开放答案误包装成 PASS。

可恢复性：checkpoint 主键为 case_id + run_index，并逐条校验 dataset_version、task SHA-256、model、provider。只按 case_id 恢复会把改题、换模型后的旧答案混入新实验，因此指纹不一致直接报错，不自动纠正。

分阶段耗时：Total = Model + Tool + Orchestration；分别报告 P50/P95。Model 计 provider await 时间，Tool 计真实工具执行时间，Orchestration = max(0, Total − Model − Tool)。当前框架没有独立队列，因此不伪造 Queue 指标。

机器证据：AGENT_OPEN_V1.json 保存无逐条答案的汇总；reports/checkpoints/agent_open/agent-open30.v1-p1b2.jsonl 保存最终 90 条 raw trace；reports/reviews/AGENT_OPEN_V1_HUMAN-p1b2.jsonl 是人工评分模板。密钥值零入库，只记录 DEEPSEEK_API_KEY 变量名；p1b1 trace 只保留为 scorer 修正的历史诊断。

5.10.15 面试高频追问：指标取舍、安全门禁与真实 Agent

追问回答主线
为什么不能只看 Recall？Recall 不关心顺序；MRR 看首个正确结果，nDCG 看整个前 k 排序，三者回答不同问题。
为什么安全不做综合分？均值会掩盖低频高损事故；安全是约束优化中的可行域，不是与质量互换的目标函数。
为什么工具指标用 multiset？集合会把重复调用压成一次，无法暴露 Agent 循环和冗余成本。
为什么 Tokens/Success 而非每请求 Token？失败请求也花钱；只看每请求可能奖励廉价失败。实际报告应同时给总成本、成功数和 Cost/Success。
LLM Judge 是否可信？安全门禁不用 Judge；结构化事实、数字、工具参数优先确定性 scorer，开放答案才用经人审校准的 Judge。
96 条够吗？比 24 条更稳，但仍是合成冻结集。它适合 PR/nightly 回归，不足以替代脱敏生产流量、人审样本和持续红队。
为什么 checkpoint 不能只记“跑到第几条”？位置索引会被数据集增删/重排破坏；按 dataset_version + schema + level + top_k 定位文件，再按 scenario.id 幂等去重，才能证明没有错续跑。
为什么不用无限并发把 live 跑快？provider 有 QPS/429，SQLite 连接默认不能跨线程共享；并发是资源约束下的优化，不是越大越好。当前通过 embedding 缓存消除重复网络 I/O，CLI 保守单 worker。
原子写和断点续跑有什么区别？原子写保证单次落盘不产生半文件；断点续跑保证跨进程恢复不重复执行。前者是局部一致性，后者是任务级幂等性。
为什么 BGE 上线前必须做 A/B？“模型更复杂”不推出“当前数据更好”。rag96 中 L2 相对 L1 的 ΔRecall=-0.01172、ΔnDCG=-0.01208，应保留 Stub 或继续调参，而不是按品牌替换。
Groundedness=1 为什么 Citation Recall 只有 0.75？Groundedness 问“答案中的 claim 是否有引用支持”；Citation Recall 问“所有 gold chunk 是否都被引用”。一个最小充分证据可支撑 claim，但不必覆盖全部相关 chunk。
为什么 scripted 和 live Agent 都要保留？scripted 隔离模型随机性，证明 Runner 控制流；live 引入真实模型，证明工具选择、参数、恢复和成本表现。两者测量对象不同，互相替代会丢失归因能力。
24/24 是否说明 DeepSeek Agent 已经满分？不是。它只说明 agent-live24.v1 受约束冻结集全部通过；没有覆盖脱敏生产分布、开放答案人审、长多轮和多次随机重复。
如何证明错误恢复是真的？工具第一次确定性返回 ToolResult.error，trace 必须出现 error→同 key 重试→ok→正确 final answer；只看最终答案或模型自述都不算恢复证据。
为什么首轮失败后可以修 scorer？先查看完整答案、实际工具、参数和状态。LCR2 已明确“无法猜测/隐私/无权限”，业务语义正确，失败来自只匹配“拒绝”的假阴性；使用新 checkpoint schema 独立重跑，避免篡改历史证据。

8.3 scope、tenant、principal、audience 的判断准则

概念大白话判权含义
tenant_id组织/公司 ID第一层组织墙：跨 tenant 永不可见。
principal_id自然人身份，格式 tenant:channel:平台用户ID表示“谁在请求”；写 user 记忆时转成 owner_id。
audience_type答案发给谁看：dm/group/threadDM 门：个人记忆必须 owner 匹配且当前是私聊才可召回。
scope='org'组织共享知识，owner_id=NULL同 tenant 内可见；不是群聊流水，也不是某个人的私密事实。
scope='user'个人记忆，owner_id=principal_id仅 owner 本人在 DM 私聊中可见；群聊中连本人自己的 user 记忆也不召回。

8.4 Dream “按 principal 分批蒸馏”到底是什么

✅ 正确理解
Dream 不再把所有人的历史揉成一个 Prompt 写全局 MEMORY；而是先按 principal_id 把 history.jsonl 分桶，每个自然人单独蒸馏。LLM 只输出候选事实文本，owner 不由 LLM 判断，而是由该批次的 principal_id 确定性继承，再以 scope='user' 写入 SQLite。
🚫 常见误解
  • principal_id 不是群聊 ID，它永远指自然人；群/话题会话 ID 属于 audience_id。
  • Dream 不自动把群聊内容总结成 org 团队知识，否则普通成员发言会被自动升级为全租户永久共享事实。
  • scope='org' 通常来自有权限的人显式调用 memory_remember(scope='org')，不是后台 Dream 猜出来的。

8.5 最终可背诵版本

visible(memory, ctx) = sameTenant ∧ active ∧ [ scope=org ∨ (scope=user ∧ owner=principal ∧ audience=dm) ]
一句人话：团队知识同组织可见；个人记忆只有本人私聊可见。近期历史另走 history 通道：私聊只看本人私聊流水，群聊只看同群流水，二者不能混淆。

9 · 压测详细报告（背压有界性）

这一节把 §7.2 的证据线 B 展开成一份完整压测报告，按 出发点 → 预期 → 设备/环境 → 怎么测 → 结果 → 面试怎么说 六段式组织。核心命题只有一句：洪峰来袭时，系统的排队不会无界堆积，而是收敛到一个可预测的上界。

9.1 出发点（为什么要做这个测试）

💡 动机
上游 nanobot 用一个全局 FIFO 信号量当并发闸门，没有 max_queue 上限。一旦某渠道瞬时灌入大量消息（群里被 @ 刷屏、机器人被压测），排队会随 burst 线性增长，内存/延迟跟着雪崩。M9 写了公平准入算法，但 M13 才发现接线位置才是关键——闸门必须在拿 session 锁之前生效，否则洪峰全堆在锁前面，max_queue 形同虚设。压测就是要用数据证明这个"有界性"真的成立，而不是靠嘴说。

9.2 预期（做之前的假设）

指标改前 baseline（无界 FIFO）改后 nanoscope（有界准入）
峰值排队 peak_queue随 burst 线性增长（≈ burst − 在飞数）收敛到 max_queue 上界，不再增长
rejection_ratio0（来者不拒，但代价是无界堆积）> 0（队满优雅拒绝，换取有界资源）
goodput（完成/秒）基线吞吐基本持平（拒绝的是"本来也扛不住"的超额请求）
🚫 可证伪纪律
如果关掉有界准入（baseline）后 peak_queue 也没暴涨，说明负载模型根本没打出洪峰，结论无效。所以 baseline 必须先翻车（peak_queue 线性堆到 117），改后才有资格说"我收敛住了"。

项配置

ℹ️ 为什么用"离散事件"而不是真打网络
真实网络压测（QPS、延迟）受机器、网卡、OS 调度干扰，不可复现，也无法在 CI 里跑。这里的目标是验证算法与接线的正确性（排队上界、公平出队、优雅拒绝），所以用受控的离散事件模型——每个请求有确定的到达时刻与服务时长，指标由 sweep-line 精确重建，每次跑结果一致，答辩时可当场复现。

为什么"有界"能成立？—— Little's Law 交叉校验

L = λ · W
逐符号：L=系统里平均"在册"请求数（在飞+排队），λ=平均到达率（个/秒），W=平均停留时间（秒）。实现用完成记录算 λ、W 得 Lpredicted=λW，再用同一批事件做 sweep-line 时间积分得 Lmeasured，比较相对误差。
诚实边界（终审 P1）：sweep-line 正确处理了跨出观测窗口的请求，但它和 λW 仍来自同一批生命周期事件；在完整观测窗内两者代数等价，所以只能叫一致性重算，不是独立物理验证。要升级成独立验证，需另采集 queue/inflight gauge 再做固定时间窗积分。有界性的直接铁证仍是 peak_queue 从 117 收敛到 32。

🎯 可能的追问与应答
  • Q：为什么不用真实 QPS 压测？A：目标是验证算法与接线的正确性，需要可复现；真实网络压测受机器/OS 干扰无法进 CI。离散事件模型每个请求有确定到达/服务时间，sweep-line 精确重建峰值，答辩可当场复跑。

10.1 出发点（威胁模型）

💡 我在防谁
多租户 Agent 面临三类真实威胁：

10.5 诚实边界（不夸大，这是加分项）

🚫 三条主动坦白的边界
① 注入测试只测静态探针残留，不等于真实攻击成功率——结构中和是数学确定的，纯自然语言只能靠模型对齐兜底，残留 5 条如实保留。
② 规模曲线 CI 用 1.96×SE：当前只有 3 个 seed，严格 95% CI 应用 Student-t（n=3 时约 4.303）或增加 seed；已列为统计 P1，不影响隔离结论（隔离是确定性的，不依赖统计显著性）。
③ 结构化包裹不能数学上消除 prompt injection——它显著降低攻击面，但不是银弹。

10.6 面试怎么说（话术）

🎤 30 秒电梯版
"我把这个 Agent 的安全隔离做成了可证伪的确定性隔离墙：可见性只由 SQL 授权 WHERE + DB CHECK + 租户化分区结构决定，检索排序永远不参与。我对记忆、最近历史、文档 RAG 三条进 prompt 的通道都做了 A/B——关掉隔离时越权曝光是 9、跨租户同名部门会泄露；打开后全部翻转成 0。文档 RAG 我还证明了隔离与检索正交：HNSW 的 ef 从 10 扫到 100，越权命中始终是 0。我特别强调所有结论都可证伪——baseline 必须先翻车，否则我不认为测试有效。"
🎯 可能的追问与应答
  • Q：怎么保证 principal 不被伪造？A：principal_id 只能来自渠道验签后的稳定平台 ID，绝不从用户消息或模型输出取；格式含 tenant 防跨租户撞 ID，出现第二个 tenant 直接 fail-closed 拒绝。
  • Q：为什么故意保留 post-filter 这个"错误"策略？A：它是反面铁证——它的候选集里含越权 id，正好证明"隔离没在召回前"会发生什么；测试断言 pre/partitioned 候选不含越权 id 而 post 含。
  • Q：76.2% 是注入抵抗率吗？A：不是，我会主动纠正。这只是静态字符串探针中和率，没调模型；纯自然语言注入的真实效果要另做红队实验。这种诚实边界我在报告里都标了。
  • Q：隔离和检索为什么必须正交？A：因为可见性是确定性的（SQL 要么命中要么不命中），检索是概率性的（向量相似度靠猜）。如果让概率性的东西决定可见性，安全就不可证明了。所以我用参数扫描实测：ef 怎么变，越权命中恒 0。
  • Q：跨租户同名部门那个 bug 怎么发现的？A：Review 时意识到旧分区键只有 project_finance，两家公司都叫 finance 会撞进同一 HNSW 子图；修复是把 tenant 加进物理分区键 (tenant_id, scope, owner_or_acl)，并加返回前的 tenant fail-closed 检查，配双租户测试——修复前稳定泄露、修复后 exposure=0。
