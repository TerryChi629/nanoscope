NanoScope:把 nanobot 改造为 Principal / Audience-aware 多用户 Agent Runtime

在开源 Agent 框架 nanobot 之上,针对其「单用户假设」被用于单组织多用户 IM Bot(飞书/Slack,群聊+私聊)时暴露的跨用户记忆泄露缺陷做魔改。承重腿是记忆隔离内核(P0)——可判定的安全不变量;延伸是 RAG 混合检索与应用层公平调度(P1),并用一套旁路评测底座量化收益。

§1.1 改进全貌 · 架构定位

核心升华:授权谓词从「只关于请求者」的 f(resource; principal),升级为「关于 (请求者, 受众, 资源) 三元」的 f(resource; principal, audience)。识别出框架里 身份 / 会话 / 受众 / 记忆作用域 从未被统一成一个安全上下文——本项目建立了这个缺失的抽象。

请求处理链路(改后)

InboundMessage
bus/events.py → IdentityResolver
nanoscope/identity.py → SecurityContext
tenant·principal·audience → FairAdmission 准入
concurrency/admission.py → search_visible 授权召回
memory/repository.py → ContextBuilder 注入

四个正交维度(identity.py:3-4):Principal(谁问)· Session(哪些消息算一段)· Audience(答案给谁看)· Memory Scope(记忆给谁看)。基线把这些混在 session_key 一个概念里,导致「谁问」和「答案给谁」被当成一回事——这正是泄露的数学根因。

§1.2 安全模型 · SecurityContext + 授权谓词

一次请求解析出一个冻结不可变的 SecurityContext(identity.py:30-55),贯穿检索/写入/准入。MVP 生效 4 字段,2 个前向兼容钩子(采集但暂不参与谓词)。

SecurityContext 字段

字段作用状态
tenant_id哪个组织生效
principal_id谁发起 = tenant:channel:uid生效
session_key哪些消息算一段生效
audience_typedm/group/thread生效
audience_id发往哪个会话前向兼容

记忆授权谓词(DM 门)

在 Repository._visibility_where 内部强制(repository.py:181-193),上层拿不到拼 WHERE 的机会:

WHERE tenant_id = :tenant
  AND status = 'active'
  AND (
    scope='org'
    OR (scope='user'
       AND owner_id=:principal
       AND audience_type='dm') )

个人记忆仅本人私聊召回;群聊语境 audience_type='group' 时整条 user 记忆被挡在召回之前。

安全红线(全程贯彻):可见性 = 确定性硬过滤(SQL WHERE + DB CHECK)。RAG 只排序,绝不决定「能不能看」。即便 FTS 倒排里混入他人条目,也被主表授权 WHERE 过滤——顺序不能反。

§2.1 基线对比 · 记忆隔离(为什么这么改)

承重腿。基线缺少长期记忆的 owner 边界(缺 non-interference 保证),多用户共用一个 bot 时个人事实跨用户可见。

✗ 基线缺陷

  • Core 全局注入:MEMORY/SOUL/USER 每轮整份塞进每个用户的 system prompt
    context.py:86-88, 166-177
  • Dream 后门(最隐蔽):read_unprocessed_history 签名无 owner 过滤,所有用户(含 1:1 私聊)历史进同一个 Dream prompt,蒸馏后写全局 MEMORY.md
    memory.py:367-369, editable_files 三文件
  • 受众越权:A 私聊说的话,A 在群里一问就被合法召回并发到群里 → 全群可见

✓ NanoScope 改动

  • SQLite 唯一动态写入口:memories 表 + DB CHECK,user 缺 owner / org 带 owner 直接写不进
  • DM 门谓词:个人记忆仅 audience_type='dm' 召回(repository.py:186-193)
  • 闭 Dream 后门:隔离下 editable_files=[],Dream 禁写三文件;USER.md 停注(memory.py:615-620)
  • M8 owner-aware:按 principal 分批独立 prompt,owner 由批次确定性继承(非 LLM 指定)
为什么这么改:owner-based 的 WHERE 挡不住「A 私聊事实进群答案」——数据库没越权,但输出受众越权。所以谓词必须加 audience 自变量。而 audience 是渠道确定性可得的(chat_type),不是概率判断,满足安全边界红线。

§2.2 基线对比 · 检索(为什么引入 RAG)

基线根本没有检索层(全仓 grep embedding|bm25|fts5|vector = 0 命中),靠「摘要压缩 + 近期窗口 + Core 全量注入」维持记忆。

✗ 基线随规模失效的三堵墙

  • Token 天花板:全量注入放不下,记忆越多注入越大
  • 语义盲区:近期窗口按时间近邻,不按相关性;老而相关的事实排在窗口外
  • 细节丢失:Consolidator 是有损摘要(memory.py:638),精确数值被抹平

✓ 隔离墙内的相关性召回

  • BM25:FTS5 trigram 影子索引(对中文 CJK 友好),在可见集合内按 bm25() 排序
  • 向量 + RRF:GLM embedding-3 补语义盲区,倒数秩融合(免调分数量纲)
  • 规模曲线:用数据界定「从什么规模该上 RAG」(拐点 M₀),而非拍脑袋
诚实边界:小规模下全量注入更简单、更确定,不强上 RAG。RAG 的必要性是规模曲线实测出来的(见 §3.3),不是预设的。

§2.3 基线对比 · 并发(为什么只改调度、不加机器)

核心命题:不做部署层水平扩展,只在单进程 asyncio 内做应用层调度优化。目标规模(几十并发)瓶颈不是机器数,而是缺调度策略——这是框架内部算法缺陷,加机器解决不了。

#基线缺陷(已核实)NanoScope 解法
① 全局 FIFO 队头阻塞:async with lock, gate:,Semaphore(3) 持有到整个 turn 结束 loop.py:974 least-in-flight 公平出队:释放名额时优先唤醒占用最少的 principal
② 无 per-principal 配额:gate 全局单一计数,刷屏用户可占满全部名额 per-principal in-flight 上限(默认 1),防单人霸占
③ 无全局有界背压:inbound bus 是无界 asyncio.Queue(),过载即雪崩 bus/queue.py:17-18 全局有界 admission 队列:队满优雅拒绝(AdmissionRejectedError,可回 retry-after)
为什么可信:改前(BaselineGate)/ 改后(FairAdmissionController)在同一台机器、同一 workload、Mock LLM 下 A/B,收益完全归因于调度算法,不被网络波动或加机器污染。

§3.1 评估体系 · 安全不变量 + 五层证据

不写「实现零泄露」(有限 Benchmark 证明不了全局)。改为安全不变量 + 五层证据,从强到经验逐层收口。

② Repository 单入口

④ 冻结攻击集

⑤ Trace 审计

+ 飞书真实 e2e

私聊落密→群里越权问(命中 0)→私聊自查(召回)。DM 门在真实飞书渠道确定性生效。

四级安全指标(最关键是第三个):forbidden_storage_hit / forbidden_retrieval_hit / forbidden_prompt_exposure / forbidden_output_hit。秘密进入他人 prompt 即算失败,不依赖模型是否愿意闭嘴。
